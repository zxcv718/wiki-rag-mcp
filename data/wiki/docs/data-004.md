# 누리 일일 정산 파이프라인 개요

## 개요
누리 일일 정산 파이프라인은 가맹점별 일 단위 정산 배치 시스템인 누리에서 하루치 결제 내역을 정산 원장으로 반영하는 배치 흐름입니다. 전체 흐름은 수집, 검증, 집계, 원장적재의 4단계로 실행됩니다.

이 문서는 각 단계의 입력과 출력, 실행 시점, 중단 조건, 운영 시 확인 지점을 정리합니다. 여기서 정산 원장은 누리가 만드는 가맹점별 정산 기준 테이블을 뜻합니다. 운영 관점에서는 전일 거래를 기준으로 당일 새벽에 처리되는 배치로 이해하면 됩니다.

## 입력과 출력
주요 입력과 출력은 아래와 같습니다.

| 구분 | 내용 |
|---|---|
| 입력 데이터 | 솔게이트 승인 데이터, 솔게이트 취소 데이터 |
| 처리 기준 | 가맹점별, 거래일 기준 일 단위 |
| 중간 산출물 | 검증 결과 집합, 집계 결과 집합 |
| 최종 산출물 | 정산 원장 최신 스냅샷 |

수집 단계에서는 솔게이트의 승인 데이터와 취소 데이터를 같은 실행 단위에서 함께 읽습니다. 승인과 취소를 분리 실행하지 않기 때문에, 특정 일자의 순정산 금액은 두 데이터가 모두 반영된 뒤에만 확정됩니다.

최종 산출물은 원장적재 단계에서 갱신됩니다. 이 단계가 끝나면 정산 원장 최신 스냅샷을 데이터 스페이스의 공용 조회 뷰로 반영합니다. 조회용 데이터는 원장적재 완료 전과 완료 후가 다를 수 있으므로, 배치 도중 수치를 비교할 때는 이 시점을 기준으로 확인합니다.

## 실행 일정
누리 일일 정산 파이프라인의 일일 실행 시작 시각은 00시 20분입니다. 수집 단계는 매일 00시 20분에 시작하며 솔게이트 승인 데이터와 취소 데이터를 함께 읽습니다.

일정 운영 원칙은 다음과 같습니다.

1. 하루에 한 번 정기 실행합니다.
2. 전일 거래를 기준으로 처리합니다.
3. 선행 단계가 정상 종료되어야 다음 단계로 진행합니다.
4. 중단 조건이 발생하면 후속 단계는 실행하지 않습니다.

실행 여부 확인은 배치 시작, 단계 전환, 종료 시점의 로그와 산출물 생성 여부를 함께 봅니다. 재실행이 필요한 경우에도 동일 거래일에 대해 중복 반영이 없는지 먼저 확인합니다.

## 단계별 처리
### 1. 수집
수집 단계에서는 솔게이트에서 승인 데이터와 취소 데이터를 읽어 처리 대상 집합을 만듭니다. 이 단계의 목적은 원천 거래를 빠짐없이 확보하는 것입니다. 거래 식별값 기준 중복 여부와 기본 형식 오류는 이 단계에서 1차로 걸러냅니다.

### 2. 검증
검증 단계에서는 수집된 거래와 정산 기준 데이터를 대조해 정합성을 확인합니다. 대표적으로 누리 정산 금액과 결제 원장이 맞지 않는 경우 SP-E2003로 집계합니다. 검증 단계에서 SP-E2003가 50건을 넘으면 파이프라인은 자동으로 중단됩니다.

자동 중단은 잘못된 집계가 후속 단계로 전파되는 것을 막기 위한 장치입니다. 따라서 이 조건이 발생하면 집계와 원장적재는 진행하지 않습니다.

### 3. 집계
집계 단계에서는 검증을 통과한 거래를 가맹점별 정산 기준으로 묶어 일 단위 결과를 계산합니다. 승인과 취소를 함께 반영해 순금액 기준 결과를 만듭니다. 이 단계의 산출물은 원장적재 전 최종 계산 결과로 사용됩니다.

### 4. 원장적재
원장적재 단계에서는 집계 결과를 정산 원장에 반영합니다. 적재가 끝난 뒤에는 정산 원장 최신 스냅샷을 데이터 스페이스의 공용 조회 뷰로 반영합니다. 운영 확인 시에는 원장 반영 완료와 조회 반영 완료를 같은 종료 기준으로 봅니다.

## 실패 시 대응
실패 대응은 단계별로 구분합니다.

1. 수집 실패
   - 솔게이트 입력 데이터 도달 여부를 먼저 확인합니다.
   - 승인 데이터와 취소 데이터 중 한쪽만 읽힌 경우에는 부분 성공으로 보지 않고 실패로 처리합니다.

2. 검증 실패
   - SP-E2003 발생 건수를 우선 확인합니다.
   - SP-E2003가 50건을 넘어서 자동 중단된 경우, 해당 거래일의 원천 데이터와 직전 정상 실행 결과를 비교합니다.
   - 원인 확인 전에는 수동 재실행을 진행하지 않습니다.

3. 집계 실패
   - 검증 결과 집합이 정상 생성되었는지 확인합니다.
   - 동일 거래가 중복 포함되었는지와 취소 반영 누락이 없는지 점검합니다.

4. 원장적재 실패
   - 적재 대상 집합과 실제 반영 건수를 비교합니다.
   - 적재 실패 후 공용 조회 뷰 반영이 수행되지 않았는지 확인합니다.

운영 중 이상이 확인되면 데이터팀 담당자에게 먼저 공유하고, 데이터 품질 이슈가 아닌 입력 데이터 이상이 의심되면 개발본부와 함께 원인을 확인합니다. 문의나 인수인계가 필요한 경우 데이터 스페이스 문서 링크와 해당 거래일, 실패 단계, 확인한 로그 시각을 함께 정리해 전달합니다.
