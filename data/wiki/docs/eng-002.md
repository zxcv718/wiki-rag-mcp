# 장애 보고서 작성 가이드

## 배경
장애 보고서는 장애의 사실 관계를 정리하고, 같은 유형의 문제를 줄이기 위한 기준 문서입니다. 개발본부 내에서 장애 내용을 빠르게 공유하고, 후속 조치의 책임과 범위를 분명히 하는 데 목적이 있습니다. 여러 팀이 함께 대응했더라도 보고서에는 한 문서 기준의 책임자와 판단 근거가 분명해야 합니다.

이 문서는 장애가 복구된 뒤 남기는 사후 기록을 대상으로 합니다. 대응 과정에서 수집한 로그, 알림, 확인 결과를 정리해 이후 검토와 재발 방지에 활용합니다. 확인된 사실과 추정을 구분해 적는 것을 원칙으로 합니다.

장애 보고서에는 DRI를 반드시 한 명 적습니다. DRI는 작업이나 장애의 직접 책임자 한 명을 뜻합니다.

## 장애 등급 기준
장애 등급은 영향 범위와 지속 시간을 함께 보고 정합니다. 등급은 사후 검토의 우선순위와 후속 조치 범위를 정하는 기준이므로, 판단 근거를 함께 남겨야 합니다.

| 등급 | 기준 | 예시 |
|---|---|---|
| S1 | 핵심 기능이 광범위하게 실패하거나 중단된 경우 | "결제 실패율 10%" 이상이 5분 넘게 이어진 경우 |
| S2 | 핵심 기능 일부에 장애가 있으나 제한적으로 우회가 가능한 경우 | 일부 가맹점에서 결제 지연이나 실패가 반복된 경우 |
| S3 | 영향 범위가 작고 국소적인 경우 | 비핵심 화면 오류나 일시적 지연 |

데이터 손상 가능성, 정산 지연 가능성, 보안 영향이 있으면 기능 영향과 별도로 본문에 분리해 적습니다. 등급 판단이 애매하면 우선 높은 등급으로 기록하고, 사후 검토에서 조정합니다.

## 보고서 항목
장애 보고서는 복구 후 2영업일 안에 작성합니다. 초안이라도 먼저 등록해 공유하고, 추가 확인 내용이 있으면 같은 문서를 갱신합니다.

보고서에는 아래 항목을 포함합니다.

1. 장애 개요
   - 발생 시각
   - 복구 시각
   - 장애 등급
   - 사용자 영향
   - 내부 영향

2. DRI
   - 직접 책임자 한 명
   - 소속 팀
   - 연락처

3. 타임라인
   - 최초 감지
   - 주요 대응
   - 임시 조치
   - 복구 완료

4. 원인
   - 직접 원인
   - 근본 원인
   - 확인 근거

5. 조치 사항
   - 이미 완료한 조치
   - 남은 후속 조치
   - 담당 팀

6. 재발 방지
   - 모니터링 보완
   - 테스트 보완
   - 운영 절차 보완

여러 팀이 대응에 참여했더라도 DRI는 한 명만 적고, 나머지 참여 팀은 조치 사항이나 타임라인에 기록합니다.

## 작성 예시
```text
제목: 2025-01-17 결제 장애 보고서

1. 장애 개요
- 발생: 2025-01-17 14:02
- 복구: 2025-01-17 14:21
- 등급: S1
- 영향: 일부 가맹점 결제 요청 실패 증가. 고객지원팀 문의 유입 증가.

2. DRI
- 김도윤
- 결제 스쿼드 페이코어
- doyun.kim@saesol.example

3. 타임라인
- 14:02 오류 증가 확인
- 14:05 대응 시작
- 14:11 임시 조치 적용
- 14:21 정상화 확인

4. 원인
- 특정 조건에서 처리 예외가 반복 발생했습니다.
- 예외 처리 누락이 직접 원인이었습니다.
- 로그와 재현 테스트로 확인했습니다.

5. 조치 사항
- 예외 처리 보완 배포를 완료했습니다.
- 경계 조건 테스트를 추가합니다.
- 모니터링 알림 조건을 보완합니다.

6. 재발 방지
- 배포 전 검증 항목에 동일 조건 확인을 추가합니다.
- 장애 타임라인 기록 방식을 통일합니다.
```

## 체크리스트
- 장애 복구 후 문서를 남겼습니까
- 복구 시점 기준으로 2영업일 안에 등록했습니까
- DRI를 한 명만 적었습니까
- 장애 등급과 판단 근거를 적었습니까
- 사용자 영향과 내부 영향을 적었습니까
- 타임라인에 주요 대응과 복구 시각을 적었습니까
- 원인과 확인 근거를 적었습니까
- 재발 방지와 후속 조치를 적었습니까
