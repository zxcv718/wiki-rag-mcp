# 은하수 프로젝트 정산 검증 규칙

## 배경
은하수 프로젝트는 누리 정산 시스템 재구축 프로젝트입니다. 누리는 가맹점별 일 단위 정산 배치 시스템이며, 기존 운영 결과를 그대로 재현하는 것이 전환의 기본 조건입니다. 정산은 원장, 수수료, 지급 결과가 서로 맞물려 있으므로 한 지표만 일치해도 전환 적합성을 보장할 수 없습니다.

이 문서는 병행 검증 시점에 어떤 기준으로 차이를 판정하고, 어떤 경우를 우선 조사 대상으로 올릴지 정리합니다. 대상 독자는 페이코어와 데이터팀이며, 운영 DB 접근이나 인프라 설정 자체는 다루지 않습니다.

## 목표와 비목표
목표는 다음과 같습니다.

1. 누리와 재구축 결과를 같은 입력 기준으로 비교합니다.
2. 전환 검증을 동일한 절차로 반복 가능하게 만듭니다.
3. 차이 발생 시 조사 우선순위를 빠르게 정합니다.

비목표는 다음과 같습니다.

1. 정산 배치의 내부 구현 방식 전체를 설명하지 않습니다.
2. 지급 실행 승인 절차를 정의하지 않습니다.
3. 인프라 배포 순서나 장애 대응 절차를 정의하지 않습니다.

## 설계
은하수 프로젝트 전환 검증은 원장 비교, 수수료 비교, 지급 파일 비교의 3개 축으로 수행합니다. 세 축은 같은 영업일 범위를 기준으로 집계하며, 비교 단위는 가맹점입니다.

| 검증 축 | 비교 대상 | 주요 확인 항목 | 차이 해석 |
|---|---|---|---|
| 원장 비교 | 결제 원장 합계와 정산 원장 합계 | 거래 건수, 승인 취소 반영, 순액 합계 | 원장 누락 또는 집계 기준 불일치 가능성 |
| 수수료 비교 | 가맹점별 수수료 계산 결과 | 과세 대상, 반올림, 수수료 합계 | 계산식 또는 기준 데이터 차이 가능성 |
| 지급 파일 비교 | 가맹점별 지급 예정 결과 | 지급 금액, 지급 제외 건, 파일 행 수 | 최종 지급 산출 차이 가능성 |

병행 검증 기간에는 기존 누리 결과와 차이가 0.1%를 넘는 가맹점이 나오면 자동으로 SP-E2003 후보 목록에 올린다. SP-E2003는 누리 정산 금액과 결제 원장이 맞지 않는 에러를 뜻합니다. 후보 목록 등록은 확정 판정이 아니라 조사 시작 조건입니다. 원장 비교에서 차이가 먼저 확인되면 수수료와 지급 파일 차이는 후행 영향으로 분류합니다.

비교 결과는 일자별 산출물로 보관합니다. 최소 보관 항목은 기준 영업일, 가맹점 식별값, 누리 결과, 재구축 결과, 차이 금액, 차이 비율, 판정 상태입니다. 수동 수정은 금지하며, 재산출 시 이전 결과를 덮어쓰지 않고 이력으로 남깁니다.

병행 검증 결과 보고는 매주 목요일 16시에 데이터팀과 페이코어가 함께 리뷰한다. 리뷰에서는 신규 차이 건, 반복 차이 건, 해소 완료 건을 나눠 보고합니다.

## 검토한 대안과 선택 이유
첫 번째 대안은 지급 파일만 비교하는 방식이었습니다. 최종 지급 결과를 바로 확인할 수 있다는 장점이 있지만, 차이 원인이 원장인지 수수료인지 분리되지 않아 조사 시간이 길어집니다.

두 번째 대안은 원장 비교만 먼저 통과시키는 단계형 방식이었습니다. 원장 안정화에는 유리하지만, 수수료 규칙 차이가 뒤늦게 드러나 전환 판단이 지연될 수 있습니다.

현재 방식은 3개 축을 같은 주기에 함께 비교합니다. 이 방식을 선택한 이유는 차이의 위치를 빠르게 좁힐 수 있고, 지급 결과만 맞는 우연한 일치를 줄일 수 있기 때문입니다.

## 남은 문제
첫째, 가맹점 단위 비교만으로는 특정 거래 유형에서 발생하는 미세한 누락을 바로 찾기 어렵습니다. 필요 시 거래 묶음 단위의 보조 조회가 필요합니다.

둘째, SP-E2003 후보가 집중되는 날에는 조사량이 급증할 수 있습니다. 이 경우 데이터팀은 집계 기준을 먼저 확인하고, 페이코어는 계산 로직 변경 여부를 우선 확인합니다.

셋째, 병행 검증 종료 시점의 합격 기준은 본 문서만으로 완결되지 않습니다. 최종 전환 판단은 누적 차이 추세와 미해결 항목의 성격을 함께 봐야 합니다. 따라서 본 문서는 차이 탐지와 분류 기준에 초점을 둡니다.
