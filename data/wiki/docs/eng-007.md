# 모아 로그·지표 조회 표준

## 배경

이 문서는 개발본부에서 모아를 통해 서비스 상태를 일관되게 확인하기 위한 조회 기준을 정리합니다. 모아는 로그·지표·트레이스를 모으는 사내 관측 플랫폼이며, 운영 이슈 확인과 PIR 작성의 공통 기준으로 사용합니다.

신규 서비스는 배포 전에 모아 대시보드 1개를 반드시 등록해야 합니다. 대시보드는 서비스 운영자가 바로 열어 현재 상태를 판단할 수 있어야 하며, 로그와 지표를 함께 확인할 수 있게 구성합니다.

등대 프로젝트 참여 서비스는 대시보드 이름을 서비스명-환경 형식으로 통일합니다. 예를 들어 solpay-prod, solbook-stg처럼 작성합니다. 참여하지 않는 서비스도 같은 형식을 따르는 것을 권장합니다.

## 조회 규칙

### 1. 로그 조회

애플리케이션 로그 레벨은 운영 환경에서 INFO 이상만 남기고 DEBUG는 스테이징에서만 켭니다. 운영 환경에서 DEBUG 로그를 상시 수집하면 조회 노이즈가 커지고 장애 분석 시간이 늘어날 수 있으므로 사용하지 않습니다.

로그를 조회할 때는 아래 순서로 범위를 좁힙니다.

1. 환경을 먼저 선택합니다.
2. 서비스 단위로 대상을 한정합니다.
3. 장애 시각 전후로 시간 범위를 줄입니다.
4. 같은 요청 흐름이 보이면 관련 로그를 연속으로 확인합니다.

운영 로그 확인 시에는 일시적인 예외 한 건보다 반복 여부와 영향 범위를 우선 봅니다. 고객지원팀이나 제품기획팀에 공유할 내용이 있으면 원문 전체를 전달하기보다 필요한 구간만 정리해 전달합니다.

### 2. 지표 조회

운영 지표의 기본 보존 기간은 90일입니다. 장기 비교가 필요하면 이 기간 안에서 기준 구간을 정해 조회합니다. 조회 시에는 현재 구간과 비교 구간의 환경이 같은지 먼저 확인합니다.

기본적으로 다음 항목을 함께 봅니다.

| 항목 | 확인 목적 |
| --- | --- |
| 요청 수 | 트래픽 변동 확인 |
| 오류 비율 | 장애 범위 판단 |
| 응답 시간 | 체감 성능 확인 |
| 자원 사용량 | 포화 여부 확인 |

PIR 작성 시에는 관련 그래프를 PNG로 함께 첨부합니다. 문서에 링크만 남기지 말고, 당시 화면 기준으로 저장한 이미지를 포함합니다.

## 예시

아래는 조회 시 사용하는 이름과 기록 방식의 예시입니다.

```text
대시보드 이름 예시
- solpay-prod
- solpay-stg
- solbook-prod

로그 확인 메모 예시
- 환경: prod
- 서비스: solpay
- 확인 시각: 2026-04-19 14:00~14:20
- 관찰 내용: INFO 이상 로그에서 같은 예외가 반복 발생함
- 추가 확인: 같은 시각 오류 비율 그래프 상승 확인
```

```sql
-- 지표 확인 전후로 운영 DB 조회가 필요한 경우 예시
-- 실제 값은 문서에 남기지 않고 필요한 조건만 기록합니다.
SELECT created_at, status
FROM payments
WHERE created_at BETWEEN <시작시각> AND <종료시각>;
```

## 예외와 공유

운영 중 일시적으로 더 자세한 로그가 필요할 수 있습니다. 이 경우에도 운영 환경의 상시 설정은 바꾸지 않고, 원인 확인이 끝나면 스테이징에서 재현해 DEBUG 로그로 보완합니다.

조회 결과를 다른 조직에 전달할 때는 받는 사람에 따라 표현을 나눕니다.

- 개발본부 내부 공유는 로그와 지표를 함께 첨부합니다.
- 고객지원팀 공유는 고객 영향과 발생 시각 중심으로 정리합니다.
- 경영진·팀장 공유는 서비스 영향, 지속 시간, 현재 상태를 먼저 적습니다.

## 체크리스트

- 신규 서비스 배포 전에 모아 대시보드 1개를 등록했습니까
- 대시보드에서 로그와 지표를 모두 확인할 수 있습니까
- 운영 환경 로그가 INFO 이상으로 수집되고 있습니까
- DEBUG 로그가 스테이징에서만 켜져 있습니까
- 등대 프로젝트 참여 서비스의 대시보드 이름이 서비스명-환경 형식입니까
- 비교하려는 지표가 90일 보존 기간 안에 있습니까
- PIR에 관련 그래프 PNG를 첨부했습니까
