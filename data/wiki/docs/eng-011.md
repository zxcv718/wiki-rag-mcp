# 코드 리뷰 가이드

## 목적과 적용 범위
이 문서는 개발본부에서 PR을 작성하고 리뷰할 때 따르는 기준을 정리한 문서입니다. 목적은 변경 내용을 빠르게 이해하고, 결함을 조기에 발견하며, 병합 기준을 일관되게 맞추는 데 있습니다.

대상은 개발본부에서 작성하는 모든 코드 변경입니다. 문서 수정, 설정 변경, 테스트 코드 추가도 PR로 관리한다면 같은 기준을 적용합니다. 긴급 대응으로 먼저 반영한 변경도 예외가 아니며, 반영 후 같은 수준의 리뷰 이력을 남겨야 합니다.

## PR 작성 원칙
PR은 하나의 목적만 담아 작게 나눠 작성합니다. 기능 추가와 리팩터링, 포맷 정리, 설정 변경을 한 PR에 섞지 않습니다. 변경 이유와 확인 방법이 분명해야 리뷰 속도와 품질이 올라갑니다.

PR 하나의 변경은 400줄 이하로 합니다. 가능하면 파일 수와 변경 범위도 함께 줄입니다. 400줄을 넘길 가능성이 있으면 선행 작업과 후속 작업으로 나눠 별도 PR로 올립니다.

PR 본문에는 아래 내용을 포함합니다.

| 항목 | 내용 |
|---|---|
| 목적 | 무엇을 왜 바꾸는지 |
| 주요 변경 | 핵심 변경점 요약 |
| 확인 방법 | 리뷰어가 확인할 절차 |
| 영향 범위 | 관련 기능, 데이터, 배포 시 주의점 |
| 보류 사항 | 이번 PR에서 다루지 않는 일 |

제목은 변경 의도가 드러나게 작성합니다. 수정, 개선 같은 표현만 쓰지 말고 대상과 목적을 함께 적습니다. 초안 단계라면 현재 상태를 분명히 적고, 병합 가능 상태가 되면 본문을 최신으로 갱신합니다.

## 리뷰 진행 원칙
PR은 리뷰어 2명이 승인해야 병합할 수 있습니다. 승인 전에 작성자가 임의로 병합하지 않습니다. 리뷰어는 변경 내용을 실제로 이해할 수 있는 사람을 우선으로 지정합니다. 영향 범위가 넓으면 해당 영역 경험이 있는 사람을 포함합니다.

리뷰 요청을 받으면 1영업일 안에 첫 응답을 합니다. 첫 응답은 승인 완료를 뜻하지 않으며, 확인 시작 여부와 예상 처리 시점을 남기는 것을 포함합니다. 바로 리뷰가 어렵다면 사유와 가능한 일정을 댓글로 남깁니다.

리뷰 의견은 사실과 근거 중심으로 작성합니다. 단순 취향보다 버그 가능성, 가독성, 테스트 누락, 운영 영향 여부를 우선 확인합니다. 작성자는 의견마다 수정 또는 답변으로 처리 상태를 남깁니다. 논의가 길어지면 변경 방향을 정리해 다시 공유합니다.

## 예시
```text
제목: 결제 취소 처리에서 중복 저장 방지 추가

목적
- 동일 요청이 반복될 때 중복 저장이 발생하지 않도록 수정합니다.

주요 변경
- 저장 전 중복 여부 확인 로직 추가
- 관련 테스트 보강

확인 방법
- 테스트 실행
- 동일 입력을 두 번 처리했을 때 결과 확인

영향 범위
- 결제 취소 처리 경로
- 기존 데이터 구조 변경 없음

보류 사항
- 성능 개선은 이번 PR 범위에서 제외합니다.
```

```text
리뷰 첫 응답 예시
- 오늘 중으로 확인 시작하겠습니다.
- 데이터 영향 여부를 먼저 보겠습니다.
- 세부 의견은 내일 오전까지 남기겠습니다.
```

## 체크리스트
### 작성자
- 변경 목적이 한 가지로 모여 있는지 확인합니다.
- 변경량이 400줄 이하인지 확인합니다.
- 목적, 주요 변경, 확인 방법, 영향 범위를 적었는지 확인합니다.
- 제목만 보고도 변경 의도를 짐작할 수 있는지 확인합니다.
- 리뷰 의견에 대한 처리 상태를 모두 남겼는지 확인합니다.

### 리뷰어
- 1영업일 안에 첫 응답을 남깁니다.
- 동작 변경, 예외 처리, 테스트 누락을 우선 확인합니다.
- 이해가 어려운 부분은 추측하지 말고 질문으로 남깁니다.
- 승인 전에 남은 우려 사항이 없는지 다시 확인합니다.

### 병합 전
- 리뷰어 2명 승인이 있는지 확인합니다.
- 열린 논의가 남아 있지 않은지 확인합니다.
- PR 설명과 실제 변경 내용이 어긋나지 않는지 확인합니다.
