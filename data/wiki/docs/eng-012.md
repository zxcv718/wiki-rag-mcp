# 솔페이 API v1 지원 종료 안내

## 개요

솔페이 API v1은 2026년 7월 31일에 지원을 종료합니다. 종료일 이후에는 v1 엔드포인트에 대한 기능 수정, 장애 대응, 문의 지원을 제공하지 않습니다. 신규 연동과 기존 연동의 변경 작업은 모두 v2 기준으로 진행해야 합니다.

이번 변경의 핵심은 인증 방식 전환입니다. v1에서 사용하던 API 키 헤더 인증은 v2에서 사용할 수 없으며, v2로 옮기려면 인증을 API 키 헤더에서 OAuth 토큰으로 바꿉니다. 엔드포인트 경로와 일부 요청 본문 형식도 함께 달라지므로, 단순한 주소 변경만으로는 전환이 완료되지 않습니다.

개발 환경과 운영 환경 모두 동일한 규칙을 적용합니다. 외부 연동 주체가 있는 경우에는 종료일 이전에 상대 시스템의 변경 일정도 함께 확인해야 합니다.

## 변경 사항

| 항목 | v1 | v2 |
|---|---|---|
| 버전 경로 | `/api/v1/...` | `/api/v2/...` |
| 인증 방식 | API 키 헤더 | OAuth 토큰 |
| 지원 상태 | 종료 예정 | 사용 권장 |
| 신규 연동 | 비권장 | 사용 |

주요 확인 항목은 아래와 같습니다.

1. 요청 헤더에서 기존 API 키 관련 값을 제거합니다.
2. 인증 서버에서 발급받은 OAuth 토큰을 `Authorization` 헤더에 포함합니다.
3. 호출 경로를 `/api/v2/` 기준으로 변경합니다.
4. 응답 필드명과 상태값 해석이 기존 구현과 같은지 점검합니다.
5. 배치, 정산, 취소 요청처럼 후속 처리에 영향이 있는 기능은 운영 전 검증을 별도로 수행합니다.

## 엔드포인트

아래 표는 자주 사용하는 대표 엔드포인트 기준입니다. 실제 적용 시에는 사용 중인 연동 범위를 함께 확인합니다.

| 기능 | v1 엔드포인트 | v2 엔드포인트 | 비고 |
|---|---|---|---|
| 결제 생성 | `POST /api/v1/payments` | `POST /api/v2/payments` | 인증 방식 변경 |
| 결제 조회 | `GET /api/v1/payments/{paymentId}` | `GET /api/v2/payments/{paymentId}` | 응답 필드 일부 상이할 수 있음 |
| 결제 취소 | `POST /api/v1/payments/{paymentId}/cancel` | `POST /api/v2/payments/{paymentId}/cancel` | 사유 필드 확인 필요 |
| 정산 조회 | `GET /api/v1/settlements` | `GET /api/v2/settlements` | 조회 조건 점검 필요 |

세부 필드 차이가 있는 경우에는 호출별 테스트를 우선합니다. 특히 응답 본문을 그대로 저장하거나 다른 시스템으로 전달하는 구현은 필드 누락과 이름 변경 여부를 반드시 확인합니다.

## 요청·응답 예시

### v2 결제 생성 요청

```http
POST /api/v2/payments HTTP/1.1
Host: api.saesol.example
Authorization: Bearer <OAuth 토큰>
Content-Type: application/json

{
  "orderId": "ORD-20251103-0001",
  "amount": 15000,
  "currency": "KRW"
}
```

### v2 결제 생성 응답

```json
{
  "paymentId": "pay_001",
  "status": "approved",
  "approvedAt": "2025-11-03T10:30:00+09:00"
}
```

### 전환 시 확인 예시

```http
GET /api/v2/payments/pay_001 HTTP/1.1
Host: api.saesol.example
Authorization: Bearer <OAuth 토큰>
Accept: application/json
```

## 오류 응답

인증 전환 과정에서 가장 많이 발생하는 오류는 인증 헤더 누락, 만료된 토큰 사용, 구버전 경로 호출입니다. 오류가 발생하면 먼저 요청 경로와 `Authorization` 헤더 포함 여부를 확인합니다.

```json
{
  "message": "unauthorized"
}
```

```json
{
  "message": "not found"
}
```

점검 순서는 아래와 같습니다.

1. 요청 주소가 `/api/v2/`로 시작하는지 확인합니다.
2. `Authorization: Bearer <OAuth 토큰>` 형식으로 전달하는지 확인합니다.
3. 서버 간 호출에서 프록시나 중간 계층이 인증 헤더를 제거하지 않는지 확인합니다.
4. 기존 v1 응답 형식에 맞춘 후처리 코드가 남아 있지 않은지 확인합니다.

전환 중 문제가 있으면 제품기획팀에 릴리스 영향 여부를 먼저 공유하고, 기술 검토가 필요하면 개발본부 내 담당자에게 문의합니다. 외부 연동 일정 조율이 필요한 경우에는 고객지원팀을 통해 전달합니다.
