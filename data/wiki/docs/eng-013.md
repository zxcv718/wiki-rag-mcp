# 브랜치 전략: 트렁크 기반 개발

## 배경
개발본부는 변경을 작게 나누고 자주 통합하는 방식을 기본으로 사용합니다. 이 문서는 트렁크 기반 개발로 전환한 뒤 저장소에서 브랜치를 운영하는 기준을 정리한 것입니다.

트렁크 기반 개발의 목적은 오래 살아 있는 브랜치를 줄이고, 통합 시점의 충돌과 배포 리스크를 낮추는 데 있습니다. 작업 단위가 작을수록 리뷰와 테스트가 쉬워지고, 장애가 발생했을 때 원인 범위를 좁히기 쉽습니다. 배포는 브랜치가 아니라 main의 상태를 기준으로 진행합니다. 배포 과정에서 단계적 노출이나 되돌리기가 필요하면 하늘을 사용합니다. 하늘은 사내 배포 도구로, 카나리 배포와 롤백을 지원합니다.

## 기본 규칙
다음 규칙을 기본값으로 적용합니다.

| 항목 | 기준 |
| --- | --- |
| 기준 브랜치 | 모든 작업 브랜치는 main에서 생성합니다 |
| 통합 주기 | 작업 브랜치는 "하루 1회 이상" main에 병합합니다 |
| 브랜치 수명 | 작업 브랜치는 "2일을 넘기지" 않습니다 |
| 미완성 기능 처리 | 사용자에게 노출되면 안 되는 코드는 "기능 플래그"로 숨깁니다 |
| 배포 기준 | 배포 가능한 상태를 main에서 유지합니다 |

작업 브랜치는 기능 전체를 한 번에 끝내기 위한 공간이 아니라, 작은 변경을 안전하게 통합하기 위한 임시 공간으로 봅니다. 따라서 브랜치가 길어지기 시작하면 작업을 더 작은 단위로 쪼개야 합니다.

미완성 기능이 있어도 스키마 변경, 내부 로직 추가, 화면 구성 요소 추가처럼 분리 가능한 부분은 먼저 병합합니다. 이때 외부 동작이 바뀌지 않도록 기능 플래그를 사용합니다. 기능 플래그가 꺼진 상태에서도 빌드, 테스트, 배포가 가능해야 합니다.

## 운영 방식
작업은 다음 순서로 진행합니다.

1. main 최신 상태를 가져옵니다.
2. main에서 작업 브랜치를 만듭니다.
3. 변경을 작은 커밋으로 나눠 반영합니다.
4. 테스트를 통과시킨 뒤 가능한 한 같은 날 main에 병합합니다.
5. 병합 후 작업 브랜치는 삭제합니다.

브랜치가 2일에 가까워지면 우선 통합 가능한 부분부터 나눠서 병합합니다. 기능 플래그 없이도 안전하게 나눌 수 있는 구조 변경, 테스트 코드, 리팩터링은 먼저 정리합니다. 반대로 대규모 변경을 한 브랜치에 오래 쌓아 두는 방식은 피합니다.

배포 직전까지 브랜치를 유지하며 한 번에 합치는 방식은 사용하지 않습니다. 배포 시점의 제어는 브랜치가 아니라 main의 변경 집합과 기능 플래그, 그리고 하늘의 배포 기능으로 처리합니다.

## 예시
아래는 일반적인 작업 흐름 예시입니다.

```bash
git checkout main
git pull origin main

git checkout -b feature/payment-summary-flag

# 작업 후 커밋
git add .
git commit -m "결제 요약 계산 로직 추가"

# main 최신 반영
git checkout main
git pull origin main
git checkout feature/payment-summary-flag
git rebase main

# 테스트 통과 후 병합
git checkout main
git merge --ff-only feature/payment-summary-flag
git push origin main
git branch -d feature/payment-summary-flag
```

기능 플래그를 사용하는 예시는 다음과 같습니다.

```python
if feature_flag_enabled("payment_summary_v2"):
    render_new_summary()
else:
    render_current_summary()
```

위와 같이 미완성 기능은 코드에 포함되더라도 기본적으로 노출되지 않게 유지합니다.

## 체크리스트
병합 전에 아래 항목을 확인합니다.

- 작업 브랜치가 main에서 시작되었는지 확인합니다.
- 브랜치가 "하루 1회 이상" main에 병합되는 흐름인지 확인합니다.
- 브랜치 수명이 "2일을 넘기지" 않는지 확인합니다.
- 미완성 기능이 있으면 "기능 플래그"로 숨겼는지 확인합니다.
- 기능 플래그가 꺼진 상태에서도 테스트와 배포가 가능한지 확인합니다.
- 병합 후 main이 즉시 배포 가능한 상태인지 확인합니다.
- 병합이 끝난 작업 브랜치를 삭제했는지 확인합니다.

예외가 필요한 경우에도 기본 원칙은 동일합니다. 브랜치를 오래 유지하는 대신 변경을 더 작은 단위로 나누고, 사용자 노출 제어는 기능 플래그와 배포 절차로 해결합니다.
