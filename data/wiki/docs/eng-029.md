# 등대 프로젝트 로그 표준

## 배경

"등대 프로젝트"는 모든 서비스의 로그·지표 형식을 맞추는 관측성 표준화 프로젝트입니다. 서비스별로 로그 키 이름과 지표 이름이 다르면 장애 탐지, 원인 추적, 운영 인수인계가 느려집니다. 특히 모아에서 여러 서비스를 함께 조회할 때 같은 의미의 값이 서로 다른 이름으로 기록되면 검색식과 대시보드를 재사용하기 어렵습니다.

이 문서는 등대 프로젝트에서 합의한 공통 로그·지표 명명 규칙을 정리합니다. 대상은 개발본부가 운영하거나 배포하는 서비스이며, 로그 포맷과 대시보드 이름, 경보 이름을 통일하는 데 목적이 있습니다. 2026년 4월 기준으로 솔게이트는 카드사·PG사와 연동하는 결제 게이트웨이 서비스이고, 누리는 가맹점별 일 단위 정산 배치 시스템입니다. 두 서비스는 2026년 4월부터 등대 프로젝트 1차 적용 대상으로 지정되어 같은 에러 코드 표기 규칙을 씁니다.

## 목표와 비목표

목표는 다음과 같습니다.

1. 모아에서 서비스 간 공통 검색이 가능하도록 로그 필드를 맞춥니다.
2. 대시보드와 경보 이름만 보고도 서비스, 환경, 의미를 식별할 수 있게 합니다.
3. 신규 서비스가 운영 전환 전에 동일한 검토 절차를 거치게 합니다.

비목표는 다음과 같습니다.

1. 개별 서비스의 비즈니스 이벤트 종류를 강제하지는 않습니다.
2. 로그 저장 기간이나 보관 정책은 이 문서에서 정하지 않습니다.
3. 배포 절차 전체를 정의하지는 않습니다.

## 설계

표준 로그는 JSON 구조를 기본으로 하며, 아래 4개 필드를 반드시 포함합니다.

| 필드 | 설명 | 예시 |
|---|---|---|
| service | 서비스를 식별하는 이름입니다. | `solgate` |
| env | 실행 환경입니다. | `prod` |
| trace_id | 요청 또는 작업 흐름을 추적하는 식별자입니다. | `3f2c...` |
| error_code | 오류가 없으면 비우거나 null로 두고, 오류가 있으면 정해진 표기값을 넣습니다. | `PAYMENT_TIMEOUT` |

필드 이름은 소문자 스네이크 케이스를 사용합니다. 같은 의미의 값을 다른 키로 중복 기록하지 않습니다. 예를 들어 `traceId`, `svc`, `environment` 같은 별도 키는 표준 로그에서는 사용하지 않습니다.

에러 코드는 영문 대문자와 밑줄만 사용합니다. 접두어를 서비스별로 다르게 두지 않고, 같은 유형의 오류는 같은 표기 규칙을 유지합니다. 이 규칙은 솔게이트와 누리에 동일하게 적용합니다. 서비스 내부에서 추가 필드가 필요하면 넣을 수 있으나, 필수 필드의 의미를 바꾸면 안 됩니다.

대시보드와 경보 이름도 같은 원칙을 따릅니다. 이름에는 최소한 서비스와 환경, 대상 지표의 의미가 드러나야 합니다. 신규 서비스는 운영 전환 2주 전까지 모아 대시보드와 경보 이름을 등대 프로젝트 규칙에 맞춰 점검받아야 합니다. 점검 요청은 설계 문서 링크와 샘플 로그를 포함해 개발 스페이스에 남깁니다.

예시 로그는 아래와 같습니다.

```json
{
  "service": "solgate",
  "env": "prod",
  "trace_id": "3f2c9b8a7d6e",
  "error_code": "PAYMENT_TIMEOUT",
  "message": "gateway request failed"
}
```

## 검토한 대안과 선택 이유

첫 번째 대안은 서비스별 자율 규칙 유지였습니다. 초기 개발 속도는 빠르지만, 모아에서 공통 검색식과 공통 대시보드를 만들기 어렵다는 문제가 있었습니다.

두 번째 대안은 필수 필드를 더 많이 두는 방식이었습니다. 예를 들어 모든 로그에 사용자 식별값이나 요청 경로를 강제하는 안을 검토했습니다. 하지만 배치성 작업과 외부 연동 작업에는 맞지 않는 경우가 많아, 최소 공통분모만 필수로 두는 편이 적절하다고 판단했습니다.

따라서 필수 범위는 4개 필드로 제한하고, 나머지는 서비스 특성에 따라 확장하도록 선택했습니다. 이 방식이 적용 난이도와 조회 일관성의 균형이 가장 좋았습니다.

## 남은 문제

첫째, 기존 서비스의 과거 로그와 신규 형식이 한동안 혼재할 수 있습니다. 모아 검색식은 전환 기간 동안 구형 키와 표준 키를 함께 고려해야 합니다.

둘째, error_code의 실제 값 목록은 서비스별 구현과 운영 경험에 따라 계속 정리해야 합니다. 표기 규칙은 같아도 값의 중복 의미나 과도한 세분화는 남은 과제입니다.

셋째, 배치 작업처럼 trace_id를 자연스럽게 만들기 어려운 경우가 있습니다. 이 경우에도 작업 단위 추적이 가능하도록 실행 단위 식별자를 trace_id에 일관되게 매핑하는 구현 가이드가 추가로 필요합니다.
