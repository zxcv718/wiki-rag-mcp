# RFC 작성과 승인 절차

## 개요
RFC는 구조 변경 전에 쓰는 설계 제안서입니다. 개발본부에서 구조 변경이 필요한 작업을 시작할 때는 구현에 앞서 RFC를 작성하고, 제목 앞에 RFC 태그를 붙여 개발 스페이스에 등록합니다.

이 문서는 RFC의 작성 기준과 승인 흐름을 정리한 안내입니다. 구현 세부 코드나 일정 관리 문서의 대체물이 아니라, 변경 이유와 영향 범위를 먼저 합의하기 위한 기준으로 사용합니다. 구조 변경의 범위에는 데이터 저장 구조, 서비스 간 호출 방식, 배포 단위 분리, 운영 방식 변경 등이 포함됩니다.

## 작성 기준
RFC 본문에는 반드시 5개 필수 항목이 있어야 합니다.

| 항목 | 작성 내용 |
| --- | --- |
| 배경 | 현재 구조의 문제, 변경이 필요한 이유, 해결하려는 범위를 적습니다. |
| 제안 | 변경하려는 구조와 기대 효과를 적습니다. 필요한 경우 구성도나 단계별 적용 방식을 포함합니다. |
| 대안 | 검토했지만 채택하지 않은 방법과 제외 이유를 적습니다. |
| 롤백 계획 | 시행 후 문제가 생겼을 때 되돌리는 방법과 영향 범위를 적습니다. |
| 보안 영향 | 권한, 접근 범위, 데이터 노출 가능성, 감사 필요 사항을 적습니다. |

작성 시에는 다음 원칙을 따릅니다.

1. 배경에는 현상만 적지 말고 변경 판단의 근거를 함께 적습니다.
2. 제안에는 대상 범위와 비대상 범위를 구분해 적습니다.
3. 대안은 최소 1개 이상 적는 것을 권장합니다.
4. 롤백 계획은 실제로 수행 가능한 절차로 적습니다.
5. 보안 영향은 해당 없음인 경우에도 그 판단 이유를 적습니다.

## 승인 절차
승인 절차는 작성, 리뷰, 수정, 승인, 시행의 5단계로 진행합니다.

1. 작성  
   작성자는 RFC를 초안으로 등록하고 변경 목적과 범위를 명확히 적습니다.

2. 리뷰  
   관련 개발자가 내용의 타당성, 영향 범위, 누락 사항을 검토합니다. 데이터 저장 구조나 조회 방식에 영향이 있으면 DB 관리자 의견을 받는 것을 권장합니다. 보안 영향이 크면 정보보안팀 검토가 필요할 수 있습니다.

3. 수정  
   작성자는 리뷰 의견을 반영해 문서를 갱신합니다. 쟁점이 남아 있으면 본문에 판단 근거를 추가합니다.

4. 승인  
   리뷰가 끝난 문서는 승인권자가 시행 가능 여부를 판단합니다. 승인 전에는 구현 완료 상태라도 운영 적용을 전제로 한 확정으로 간주하지 않습니다.

5. 시행  
   승인된 RFC를 기준으로 변경을 시행합니다. 운영 트래픽에 영향을 주는 RFC는 승인 뒤에도 CAB 검토를 마쳐야 시행할 수 있습니다.

## 예시
```md
제목: [RFC] 정산 배치 저장 구조 분리

배경
기존 저장 구조는 조회와 적재가 같은 테이블에 집중되어 있어 배치 시간대에 지연이 발생합니다.

제안
적재용 테이블과 조회용 테이블을 분리하고, 배치 완료 후 조회용 테이블을 갱신합니다.

대안
1. 인덱스 추가
   단기 개선은 가능하지만 적재 부하를 줄이지 못해 제외합니다.
2. 조회 캐시 확대
   일부 조회에는 유효하지만 근본 원인 해결이 어려워 제외합니다.

롤백 계획
문제 발생 시 조회 대상을 기존 테이블로 되돌리고, 분리한 적재 경로를 중지합니다.

보안 영향
접근 권한 체계는 기존과 동일합니다. 다만 신규 테이블에 대한 권한 설정 누락 여부를 점검합니다.
```

## 체크리스트
- 제목 앞에 RFC 태그를 붙여 개발 스페이스에 등록했는지 확인합니다.
- 본문에 5개 필수 항목이 모두 있는지 확인합니다.
- 제안 범위와 제외 범위가 구분되어 있는지 확인합니다.
- 롤백 계획이 실제 절차 수준으로 작성되었는지 확인합니다.
- 보안 영향에 대한 판단이 빠지지 않았는지 확인합니다.
- 운영 트래픽 영향 여부를 확인하고, 해당하면 CAB 검토 필요 여부를 함께 기록합니다.
