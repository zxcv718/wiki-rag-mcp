# Git 브랜치 전략 (Git Flow)

## 배경

이 문서는 개발본부에서 사용하는 Git 브랜치 운영 기준을 정리한 것입니다. 기본 원칙은 개발, 배포 준비, 긴급 수정을 분리해 변경 이력을 명확하게 유지하는 데 있습니다. 일상적인 기능 개발은 개발 라인에서 진행하고, 배포 직전 검증은 별도 브랜치에서 수행하며, 운영 중 긴급 수정은 안정 브랜치에서 바로 분기합니다.

브랜치 전략은 코드 리뷰 방식이나 담당 조직과 무관하게 동일하게 적용합니다. 다만 실제 배포 일정과 QA 진행 순서는 제품기획팀, 고객지원팀과 협의할 수 있습니다.

## 브랜치 구성과 규칙

주요 브랜치는 아래와 같이 사용합니다.

| 브랜치 | 용도 |
| --- | --- |
| main | 운영 반영 기준 브랜치입니다. 배포 완료 상태를 유지합니다. |
| develop | 다음 배포를 위한 통합 개발 브랜치입니다. |
| feature/* | 기능 개발용 브랜치입니다. |
| release/* | 배포 전 점검과 QA용 브랜치입니다. |
| hotfix/* | 운영 장애나 긴급 결함 수정용 브랜치입니다. |

운영 규칙은 다음과 같습니다.

1. 기능 브랜치는 반드시 "develop 브랜치"에서 생성합니다.
2. 기능 개발이 끝나면 feature 브랜치를 develop으로 병합합니다.
3. 배포 전에 "release 브랜치"를 만들어 QA를 합니다.
4. QA 중 발견된 수정 사항은 release 브랜치에 반영합니다.
5. 배포가 끝나면 release 브랜치의 변경을 main과 develop에 모두 반영합니다.
6. 운영 중 긴급 수정이 필요하면 main에서 "hotfix 브랜치"를 딴다.
7. hotfix 수정이 배포되면 변경 사항을 main과 develop에 모두 반영합니다.

브랜치 이름은 목적이 드러나도록 작성합니다. 예를 들어 기능 개발은 `feature/payment-cancel`, 배포 준비는 `release/2024-06`, 긴급 수정은 `hotfix/login-error`처럼 씁니다. 이름 형식은 팀 상황에 따라 달라질 수 있지만, 같은 저장소 안에서는 일관성을 유지합니다.

## 작업 흐름 예시

일반적인 기능 개발과 배포 흐름 예시는 아래와 같습니다.

```bash
# 기능 개발 시작
git checkout develop
git pull origin develop
git checkout -b feature/payment-cancel

# 개발 완료 후 반영
git checkout develop
git pull origin develop
git merge --no-ff feature/payment-cancel
git push origin develop

# 배포 준비
git checkout develop
git pull origin develop
git checkout -b release/2024-06

# QA 수정 반영 후 배포 완료 처리
git checkout main
git pull origin main
git merge --no-ff release/2024-06
git push origin main

git checkout develop
git pull origin develop
git merge --no-ff release/2024-06
git push origin develop
```

긴급 수정 흐름 예시는 아래와 같습니다.

```bash
# 긴급 수정 시작
git checkout main
git pull origin main
git checkout -b hotfix/login-error

# 수정 후 운영 반영
git checkout main
git pull origin main
git merge --no-ff hotfix/login-error
git push origin main

# 개발 라인에도 동일 반영
git checkout develop
git pull origin develop
git merge --no-ff hotfix/login-error
git push origin develop
```

## 주의사항

release 브랜치가 만들어진 뒤에는 새로운 기능을 추가하지 않습니다. 이 시점부터는 QA 대응, 배포 문서 보완, 치명도 높은 결함 수정만 반영합니다. 배포 범위를 바꾸면 검증 결과가 흔들릴 수 있기 때문입니다.

hotfix 브랜치는 긴급한 운영 이슈 해결에만 사용합니다. 일반 기능 개선이나 리팩터링은 hotfix로 진행하지 않습니다. 또한 hotfix를 main에만 반영하고 develop에 누락하면 다음 배포에서 동일 문제가 재발할 수 있으므로 반드시 양쪽 반영 여부를 확인합니다.

## 체크리스트

배포 전에는 아래 항목을 확인합니다.

- 기능 브랜치가 develop 기준으로 생성되었는지 확인합니다.
- develop에 반영된 기능만 release 브랜치에 포함했는지 확인합니다.
- release 브랜치에서 QA 결과가 반영되었는지 확인합니다.
- 배포 후 release 변경 사항이 main과 develop에 모두 병합되었는지 확인합니다.
- 긴급 수정의 경우 hotfix 시작점이 main인지 확인합니다.
- hotfix 배포 후 develop 반영이 누락되지 않았는지 확인합니다.
