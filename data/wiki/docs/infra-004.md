# 등대 프로젝트 로그 필드 매핑

## 목적과 범위
이 문서는 등대 프로젝트의 로그 필드 매핑 원칙을 설명합니다. 등대 프로젝트는 모든 서비스의 로그·지표 형식을 맞추는 관측성 표준화 프로젝트입니다. 본 문서는 서비스별 원본 로그를 공통 스키마에 맞게 변환할 때 지켜야 할 기준과 검증 방법만 다룹니다.

필수 로그 필드의 목록과 각 필드의 채움 여부 기준은 별도 문서를 따릅니다. 여기서는 이미 정의된 필드에 어떤 값을 어떤 방식으로 넣을지에 집중합니다. 적용 대상은 개발본부에서 운영하는 서비스 로그이며, 모아로 수집되는 데이터를 기준으로 판단합니다. 모아는 로그·지표·트레이스를 모으는 사내 관측 플랫폼입니다.

## 매핑 원칙
공통 스키마로 변환할 때는 원본 의미를 바꾸지 않는 것을 우선합니다. 값의 형식을 맞추더라도 원문 식별 정보는 유지해야 합니다.

| 항목 | 매핑 원칙 |
|---|---|
| 시각 값 | 모든 시각 값은 UTC 기준 ISO 8601 형식으로 기록합니다. 애플리케이션 내부 시간대와 무관하게 저장 시점에는 UTC로 변환합니다. |
| 문자열 값 | 사람이 읽는 메시지는 가공하지 않고 기록합니다. 앞뒤 공백 제거 외의 정규화는 하지 않습니다. |
| 코드 값 | 서비스가 반환한 코드나 외부 연동 결과 코드는 원문을 유지합니다. 의미가 같은 다른 코드로 치환하지 않습니다. |
| 숫자 값 | 숫자형 필드는 문자열로 바꾸지 않습니다. 단, 원본이 문자열인 경우에는 별도 파서에서 변환 실패를 기록합니다. |

에러 코드는 대표적인 주의 항목입니다. 솔게이트의 에러는 PRJ-204와 GW-429처럼 원문 코드를 그대로 error_code 필드에 기록해야 합니다. 메시지 본문에만 남기거나 내부 분류명으로 바꾸면 안 됩니다.

## 데이터 흐름과 검증
데이터 흐름은 다음 순서로 봅니다.

1. 서비스가 구조화 로그를 출력합니다.
2. 수집기가 로그를 받아 공통 스키마로 매핑합니다.
3. 매핑된 로그가 모아로 적재됩니다.
4. 검증 샘플로 필드 누락, 형식 오류, 코드 보존 여부를 확인합니다.

검증 샘플은 서비스별 최근 요청 500건을 기준으로 추출합니다. 최근 요청은 운영 트래픽 기준이며, 재처리 로그나 수동 테스트 로그는 포함하지 않습니다. 샘플 검토 시에는 다음 항목을 확인합니다.

- 시각 값이 UTC 기준 ISO 8601 형식인지 확인합니다.
- error_code가 원문 그대로 들어갔는지 확인합니다.
- 동일 요청에서 필드명이 일관되게 채워졌는지 확인합니다.
- 원본 로그와 모아 적재 결과 사이에 값 손실이 없는지 확인합니다.

## 완료 판정 기준
등대 프로젝트 적용 서비스는 모아에서 로그 수집 누락률이 0.1% 이하일 때만 완료로 판정합니다. 누락률은 단순 전송 성공 여부가 아니라, 서비스에서 출력된 로그 수와 모아에서 확인된 로그 수를 비교해 계산합니다.

완료 판정 전에는 다음을 함께 확인합니다.

- 검증 샘플에서 형식 오류가 반복되지 않아야 합니다.
- 에러 코드가 치환 없이 유지되어야 합니다.
- 시각 값의 시간대 혼선이 없어야 합니다.

누락률 기준을 만족하지 못하면 필드 매핑이 맞더라도 완료로 보지 않습니다. 이 경우 수집 경로와 변환 규칙을 먼저 점검합니다.

## 운영 시 주의점
매핑 로직은 서비스 코드와 수집기 설정에 나뉘어 있을 수 있습니다. 두 위치에서 같은 필드를 중복 가공하면 값 불일치가 생기므로 한 곳에서만 책임지도록 유지합니다.

운영 중 장애 분석을 위해 메시지와 코드의 원문 보존이 중요합니다. 특히 솔게이트 연동 오류는 error_code를 기준으로 집계되는 경우가 많으므로, PRJ-204나 GW-429를 다른 분류값으로 바꾸지 않습니다.

문의나 변경 제안은 플랫폼·SRE 스페이스의 관련 문서에 남기고, 적용 전에는 모아에서 샘플 확인 결과를 함께 첨부합니다. 문서상 예시가 필요한 경우 민감 정보는 제거하고 `<비밀번호>` 같은 자리표시자를 사용합니다.
