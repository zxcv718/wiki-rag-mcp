# 파도 프로젝트 1차 전환 회고

## 요약
2026-05 첫 전환은 파도 프로젝트의 시작 단계로 진행했으며, 대상은 내부 운영 도구 3개였습니다. 고객 트래픽을 직접 받는 서비스는 포함하지 않았습니다. 전환 자체는 계획한 순서대로 마쳤고, 하늘을 통한 배포와 복귀 절차도 확인했습니다. 다만 전환 후 가장 큰 문제는 모아의 트레이스 샘플링 비율이 예상보다 높게 적용된 점이었습니다. 이로 인해 필요한 요청 흐름을 바로 찾지 못하는 경우가 늘었고, 장애나 성능 저하 징후를 확인하는 진단 시간이 평균적으로 25분 늘어났습니다.

운영 중 치명적인 중단은 없었고, 하늘 롤백은 1건 실행됐으며 서비스 중단 없이 이전 환경으로 복귀했습니다. 이번 회고의 초점은 전환 성공 여부보다, 관측 설정과 비밀값 갱신 작업이 배포 흐름에 과도하게 결합되어 있었다는 점을 확인한 데 있습니다.

## 영향
이번 전환의 영향은 외부 고객보다는 내부 운영자와 개발자에게 집중됐습니다.

- 내부 운영 도구 응답 지연이나 일시적 오류가 간헐적으로 발생했습니다.
- 모아에서 트레이스를 찾는 시간이 길어져 원인 파악이 늦어졌습니다.
- 배포 직후 확인 절차가 길어지면서 플랫폼·SRE팀과 개발본부의 대기 시간이 증가했습니다.
- 고객 트래픽을 직접 받는 서비스는 전환 대상이 아니어서 대외 장애로 이어지지는 않았습니다.

영향 범위가 제한적이었던 점은 다행이었지만, 관측 신뢰도가 낮아지면 이후 고객 대상 서비스 전환에서 같은 문제가 더 크게 나타날 수 있다는 점을 확인했습니다.

## 원인
가장 큰 원인은 관측 설정 검증이 기능 동작 검증보다 뒤에 배치된 점입니다. 파도 프로젝트는 운영 서버를 쿠버네티스로 옮기는 프로젝트인데, 이번에는 애플리케이션 기동과 연결 확인에 집중한 반면 모아 설정이 실제 운영 점검에 충분한지 사전에 검증하지 못했습니다. 그 결과 트레이스 샘플링 비율이 높아도 배포 직후에는 통과로 보였고, 실제 진단 단계에서 문제로 드러났습니다.

두 번째 원인은 배포 작업과 비밀값 갱신 작업의 결합입니다. 금고는 비밀값을 보관하는 비밀 관리 시스템인데, 새 환경 배포 잡과 갱신 주기가 맞물리면서 배포 직후 상태 확인이 불안정해졌습니다. 값 자체의 오류는 아니었지만, 변경 시점이 겹치면 원인 분리가 어려워졌습니다.

## 잘한 점과 아쉬운 점
잘한 점은 다음과 같습니다.

- 고객 트래픽을 직접 받는 서비스를 제외하고 내부 운영 도구부터 전환해 영향 범위를 제한했습니다.
- 하늘의 롤백 절차를 실제로 사용해 복귀 가능성을 확인했습니다.
- 플랫폼·SRE팀과 개발본부가 같은 화면을 보며 판단해 의사결정 지연을 줄였습니다.

아쉬운 점은 다음과 같습니다.

- 모아의 샘플링 설정을 사전 점검 항목으로 강제하지 못했습니다.
- 전환 완료 기준이 기동 여부 중심이어서 운영 진단 가능성까지 포함하지 못했습니다.
- 배포와 비밀값 갱신이 겹칠 때의 확인 순서가 문서화되어 있지 않았습니다.
