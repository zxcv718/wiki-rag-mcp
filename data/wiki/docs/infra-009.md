# 파도 프로젝트 전환 체크리스트

## 목적과 적용 범위
이 문서는 파도 프로젝트 전환 전에 확인할 항목과 전환 직후 운영 조건을 정리합니다. 여기서 파도 프로젝트는 운영 서버를 쿠버네티스로 옮기는 프로젝트를 뜻합니다. 대상 독자는 플랫폼·SRE팀과 개발본부입니다.

이 문서는 서비스별 상세 전환 조건을 새로 정의하지 않습니다. 실제 승인 기준은 관련 운영 기준과 변경 절차에 따릅니다. 본 문서는 전환 준비 상태를 빠르게 확인하고, 누락 없이 CAB 안건을 올리기 위한 체크리스트로 사용합니다. CAB는 운영 변경을 승인하는 변경 승인 위원회를 뜻합니다.

## 전환 대상 선정과 일정 확정
파도 프로젝트 전환 후보 서비스 목록은 플랫폼·SRE팀이 분기마다 갱신합니다. 후보 목록에는 서비스명, 운영 형태, 상태 저장 여부, 외부 의존성, 예상 위험도를 함께 적습니다.

전환 일정은 서비스별로 정기 CAB 안건으로 올려 확정합니다. 개발 담당자는 안건 등록 전에 아래 자료를 준비합니다.

1. 현재 운영 구성과 쿠버네티스 배치 구성 비교
2. 배포 및 되돌리기 절차
3. 모니터링 항목과 알림 기준
4. 데이터 저장 방식과 운영 DB 영향 검토
5. 고객지원팀 공유가 필요한 예상 문의 유형

정기 CAB 상정 전에는 플랫폼·SRE팀과 서비스 담당자가 사전 검토를 진행합니다. 사전 검토에서 미비점이 있으면 해당 회차 안건에서 제외할 수 있습니다.

## 구성 요소와 의존 서비스 점검
전환 전에는 아래 항목을 서비스 단위로 확인합니다.

| 구분 | 확인 항목 | 확인 주체 |
|---|---|---|
| 애플리케이션 | 무중단 배포 가능 여부, 시작 및 종료 처리, 환경 변수 정리 | 개발본부 |
| 인프라 | CPU·메모리 요청량, 스토리지 사용, 네트워크 정책 | 플랫폼·SRE팀 |
| 데이터 | 상태 저장 여부, 운영 DB 연결 방식, 세션 저장 위치 | 개발본부, DB 관리자 |
| 운영 | 로그 수집, 메트릭 노출, 장애 시 되돌리기 절차 | 플랫폼·SRE팀 |
| 대외 대응 | 전환 중 공지 필요 여부, 문의 대응 문안 | 제품기획팀, 고객지원팀 |

상태 저장 서비스는 특히 운영 DB와의 연결 특성을 먼저 확인합니다. 연결 풀 크기, 최대 동시 연결 수, 재시도 동작이 바뀌면 전환 후 부하 양상이 달라질 수 있습니다. 상태 저장 서비스는 운영 DB 연결 수 상한을 이전 대비 10% 이내 차이로 유지해야 전환 승인을 받을 수 있습니다.

## 데이터 흐름과 전환 절차
전환 전에는 요청 흐름과 데이터 저장 흐름을 문서로 정리합니다. 최소한 아래 내용을 포함합니다.

1. 외부 요청이 애플리케이션에 도달하는 경로
2. 애플리케이션이 운영 DB를 조회하거나 저장하는 시점
3. 비동기 작업이 있으면 실행 주체와 실패 시 재처리 방식
4. 로그와 메트릭이 수집되는 위치

전환 당일 절차는 다음 순서로 진행합니다.

1. 최종 배포 산출물을 확인합니다.
2. 쿠버네티스 배치 설정을 적용합니다.
3. 기동 직후 헬스 체크와 기본 기능을 확인합니다.
4. 운영 DB 연결 수와 응답 시간 변화를 확인합니다.
5. 이상이 없으면 트래픽을 유지하고, 이상이 있으면 즉시 되돌리기 절차를 실행합니다.

전환 중 설정값을 임의로 추가 변경하지 않습니다. 변경이 필요하면 CAB 안건 범위에 포함했는지 먼저 확인합니다.

## 운영 시 주의점
전환 후 첫 7일은 플랫폼·SRE팀이 일일 점검 로그를 남깁니다. 점검 로그에는 최소한 다음 항목을 포함합니다.

- 전일 장애 또는 경고 발생 여부
- 자원 사용량 추이
- 운영 DB 연결 수 변화
- 재시작 발생 여부
- 되돌리기 필요성 검토 결과

개발 담당자는 점검 기간 동안 문의 대응 가능 상태를 유지합니다. 고객 영향이 있는 이상 징후가 보이면 플랫폼·SRE팀, 개발본부, 고객지원팀이 같은 날 안에 공유합니다. 점검 기간 중 경미한 설정 수정이 필요하더라도 운영 안정성에 영향을 줄 수 있으므로 변경 이력과 검토 의견을 함께 남깁니다.

문서 보완이나 체크리스트 수정이 필요하면 플랫폼·SRE팀 문서 담당자에게 saesol.example 메일로 요청합니다.
