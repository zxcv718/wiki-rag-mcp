# 대용량 테이블 마이그레이션 절차

## 언제 사용하는가
운영 중인 MySQL 테이블의 스키마 변경이 필요하고, 대상 테이블의 행 수가 많아 직접 `ALTER TABLE` 수행 시 잠금 또는 장시간 부하가 우려될 때 사용합니다. 특히 1천만 행이 넘는 테이블은 gh-ost로 스키마를 바꿉니다.

이 문서는 컬럼 추가, 인덱스 추가, 기본값 변경처럼 데이터 구조를 바꾸는 작업에 적용합니다. 애플리케이션 배포와 함께 동작 변경이 필요한 경우에는 제품기획팀의 릴리스 일정과 충돌하지 않도록 먼저 조율합니다.

작업은 새벽 2시~5시에 합니다. 작업 전에 CAB 승인을 받습니다. CAB는 운영 변경을 승인하는 변경 승인 위원회입니다.

## 사전 확인
작업 시작 전 아래 항목을 확인합니다.

| 항목 | 확인 내용 |
|---|---|
| 변경 목적 | 변경할 컬럼, 인덱스, 제약 조건과 기대 효과를 문서로 정리했는지 확인합니다. |
| 영향 범위 | 사용하는 서비스, 배치, 조회 쿼리, 쓰기 트래픽 영향을 확인합니다. |
| 승인 | CAB 승인 완료 여부를 확인합니다. |
| 담당자 | 플랫폼·SRE팀 작업자, 개발본부 담당 개발자, DB 관리자 연락처를 확보합니다. |
| 복제 상태 | 복제 지연, 장애, 디스크 여유 공간을 확인합니다. |
| 되돌리기 | 원복 가능한 DDL과 중단 기준을 준비합니다. |

추가로 다음을 준비합니다.

1. 대상 테이블의 현재 스키마를 저장합니다.
2. 예상 실행 시간을 산정합니다.
3. 고객지원팀에 문의 증가 가능성을 공유합니다.
4. 데이터팀이 해당 테이블을 읽는 배치가 있으면 작업 시간 충돌 여부를 확인합니다.

## 작업 절차
아래 예시는 MySQL에서 gh-ost를 사용하는 기본 절차입니다. 실제 값은 환경에 맞게 치환합니다.

```bash
mysql -h <writer-host> -u <user> -p<비밀번호> -e "SHOW CREATE TABLE <db>.<table>\G"
mysql -h <writer-host> -u <user> -p<비밀번호> -e "SHOW SLAVE STATUS\G"
mysql -h <writer-host> -u <user> -p<비밀번호> -e "SELECT COUNT(*) FROM <db>.<table>;"
```

1. 대상 테이블 스키마와 복제 상태를 확인합니다.
2. 변경 SQL을 확정하고 개발본부 담당자와 최종 검토합니다.
3. 트래픽이 낮아진 시점에 gh-ost를 dry-run으로 먼저 실행합니다.
4. 이상이 없으면 실제 마이그레이션을 시작합니다.
5. 진행 중 복제 지연, 에러 로그, 애플리케이션 오류율을 계속 확인합니다.

```bash
gh-ost \
  --host=<writer-host> \
  --port=3306 \
  --user=<user> \
  --password=<비밀번호> \
  --database=<db> \
  --table=<table> \
  --alter="ADD COLUMN <column_name> VARCHAR(32) NULL" \
  --allow-on-master \
  --cut-over=default \
  --exact-rowcount \
  --default-retries=120 \
  --execute
```

작업 중 부하가 급증하거나 복제 지연이 커지면 즉시 중단 여부를 판단합니다. 애플리케이션에서 신규 컬럼을 즉시 사용하지 않도록 배포 순서를 사전에 맞춰야 합니다.

## 결과 확인
작업 완료 후 아래 순서로 확인합니다.

1. `SHOW CREATE TABLE`로 변경 사항이 반영되었는지 확인합니다.
2. 주요 읽기, 쓰기 쿼리를 실행해 오류가 없는지 확인합니다.
3. 복제 지연이 정상 범위로 회복되었는지 확인합니다.
4. 애플리케이션 로그에 스키마 관련 오류가 없는지 확인합니다.
5. 작업 결과와 종료 시각을 문서에 남깁니다.

```bash
mysql -h <writer-host> -u <user> -p<비밀번호> -e "SHOW CREATE TABLE <db>.<table>\G"
mysql -h <writer-host> -u <user> -p<비밀번호> -e "SELECT COUNT(*) FROM <db>.<table>;"
```

## 되돌리기 및 에스컬레이션
변경 후 오류가 발생하면 애플리케이션 영향도를 먼저 확인하고, 신규 스키마 의존 배포가 있으면 사용을 중지합니다. 원복이 가능한 변경이면 사전에 준비한 반대 방향 DDL로 복구합니다. gh-ost 수행 중이면 즉시 중단하고 현재 상태를 보존한 뒤 DB 관리자와 함께 절단 시점 전후 상태를 점검합니다.

다음 경우에는 즉시 에스컬레이션합니다.

- 복제 지연이 지속되어 서비스 영향이 예상될 때
- 쓰기 오류 또는 조회 장애가 발생할 때
- 디스크 여유 공간 부족이 감지될 때
- 원복 절차만으로 복구 판단이 어려울 때

에스컬레이션 순서는 플랫폼·SRE팀 내 작업 담당자, DB 관리자, 개발본부 담당 개발자 순으로 진행합니다. 서비스 영향이 확인되면 고객지원팀에도 즉시 공유합니다. 작업 종료 후에는 CAB 승인 건에 결과를 기록합니다.
