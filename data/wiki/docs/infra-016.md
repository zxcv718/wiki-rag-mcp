# 솔북 예약 중복 오류 대응 런북

## 언제 사용하는가
이 문서는 솔북에서 같은 예약 슬롯이 두 번 잡히는 현상이 발생했을 때 사용합니다. "BK-4010"은 같은 매장과 같은 예약 슬롯에서 10분 안에 중복 예약 레코드가 2건 이상 생기면 의심합니다. 고객 제보로 시작할 수도 있고, 운영 로그 확인 중 먼저 발견할 수도 있습니다.

초기 대응 목적은 전체 쓰기 차단이 아니라 중복 생성 경로를 빠르게 멈추고, 이미 생성된 예약과 결제 연동 영향을 확인하는 것입니다. 1차 대응은 플랫폼·SRE팀이 수행하고, 원인 확인이 필요한 경우 개발본부와 DB 관리자에게 이어서 전달합니다.

## 사전 확인
아래 항목을 먼저 확인합니다.

| 확인 항목 | 확인 내용 | 담당 |
|---|---|---|
| 중복 여부 | 같은 매장, 같은 예약 슬롯, 10분 안 중복 생성인지 확인합니다 | 플랫폼·SRE팀 |
| 영향 범위 | 단일 매장인지 여러 매장인지 확인합니다 | 플랫폼·SRE팀 |
| 결제 연동 | 예약에 솔페이 예약 결제 연동 주문이 포함되는지 확인합니다 | 플랫폼·SRE팀 |
| 데이터 상태 | 중복 레코드 수와 생성 시각을 확인합니다 | DB 관리자 |
| 최근 변경 | 관련 기능 플래그 변경 여부를 확인합니다 | 개발본부 |

솔페이 예약 결제 연동 주문이 포함된 BK-4010은 고객지원팀에 환불 가능성 안내 문구를 즉시 전달해야 합니다. 전달 문구는 아래 예시를 사용합니다.

> 동일 예약 슬롯에 중복 예약이 확인되어 현재 확인 중입니다. 예약 결제가 함께 발생했을 가능성이 있어 환불 여부를 우선 점검하겠습니다. 확정 전까지 추가 결제나 예약 변경은 안내 후 진행해 주시기 바랍니다.

## 단계별 대응
1. 중복 생성 경로의 기능 플래그를 비활성화합니다. BK-4010 대응 1단계는 솔북 API 쓰기 차단이 아니라 중복 생성 경로의 기능 플래그를 30분 동안 비활성화하는 것입니다.
2. 영향 범위를 조회합니다.
3. 결제 연동 주문 포함 여부를 확인하고 고객지원팀에 즉시 공유합니다.
4. 개발본부와 DB 관리자에게 조사 요청을 남깁니다.

```bash
# 1) 기능 플래그 비활성화
ssh <계정>@<호스트>
export BOOKING_DUP_PATH_FLAG=off
export BOOKING_DUP_PATH_FLAG_TTL="30m"
# 적용 후 서비스 설정 반영 절차를 수행합니다.

# 2) 최근 중복 후보 조회
psql -h <호스트> -U <계정> -d <DB명> <<'SQL'
SELECT store_id, slot_at, COUNT(*) AS dup_count,
       MIN(created_at) AS first_created_at,
       MAX(created_at) AS last_created_at
FROM reservations
WHERE created_at >= NOW() - INTERVAL '1 day'
GROUP BY store_id, slot_at, date_trunc('10 minutes', created_at)
HAVING COUNT(*) >= 2
ORDER BY last_created_at DESC;
SQL

# 3) 결제 연동 포함 건 조회
psql -h <호스트> -U <계정> -d <DB명> <<'SQL'
SELECT reservation_id, store_id, slot_at, created_at
FROM reservations
WHERE created_at >= NOW() - INTERVAL '1 day'
  AND payment_linked = true
ORDER BY created_at DESC;
SQL
```

사내 메신저 공유 예시는 아래와 같습니다.

```text
[공유] 솔북 BK-4010 의심 건 확인
- 범위: <단일 매장/복수 매장>
- 최초 확인 시각: <시각>
- 조치: 중복 생성 경로 기능 플래그 30분 비활성화
- 솔페이 연동 포함 여부: <있음/없음>
- 고객지원팀 전달: <완료/예정>
- 추가 확인 요청: 개발본부, DB 관리자
```

## 결과 확인과 되돌리기
조치 후에는 같은 매장과 같은 예약 슬롯에서 신규 중복 생성이 멈췄는지 확인합니다. 기능 플래그 비활성화 시간 동안 신규 예약 생성 자체가 아니라 중복 생성 경로만 억제되었는지 함께 봅니다. 고객지원팀에는 중복 예약 정리 대상과 결제 영향 여부를 다시 전달합니다.

30분 경과 후 원인 미확인 상태라도 중복이 더 발생하지 않으면 기능 플래그 복구 여부를 개발본부와 합의합니다. 복구 전에는 최근 생성 건을 한 번 더 조회합니다.

```bash
# 기능 플래그 복구
ssh <계정>@<호스트>
export BOOKING_DUP_PATH_FLAG=on
# 적용 후 서비스 설정 반영 절차를 수행합니다.
```

복구 직후 동일 현상이 재발하면 다시 비활성화하고 에스컬레이션 절차로 넘어갑니다.

## 에스컬레이션
아래 조건 중 하나라도 만족하면 즉시 에스컬레이션합니다.

- 여러 매장에서 동시에 발생합니다.
- 기능 플래그 비활성화 중에도 중복이 계속 생깁니다.
- 솔페이 예약 결제 연동 주문이 포함되어 고객 영향이 큽니다.
- 데이터 정리가 수동으로 끝나지 않거나 운영 DB 작업이 필요합니다.

에스컬레이션 대상은 개발본부, DB 관리자, 제품기획팀, 고객지원팀 순으로 포함합니다. 정보보안팀은 보안 이슈 정황이 있을 때만 추가합니다. 장애 사후 검토 회의와 그 문서인 PIR은 재발 방지 조치가 필요한 경우 작성합니다. BK-4010이 하루 5건을 넘기면 다음 영업일 안에 PIR 일정을 잡습니다.
