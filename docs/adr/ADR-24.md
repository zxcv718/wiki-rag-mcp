# ADR-24. 인가 서버는 위키 서비스 안의 Spring 인가 서버, 클라이언트는 CIMD와 사전 등록으로 받음

- 상태: 확정
- 주요 대안: Keycloak, 관리형 인증 서비스, 별도 Spring 인가 서버
- 출처: 설계서 3. MCP 인터페이스 설계

MCP 명세(2026-07-28)에서 MCP 서버는 OAuth 리소스 서버이고, 로그인과 토큰 발급은 별도의 인가 서버가 맡습니다. 인가 서버는 메타데이터 공개(RFC 8414 또는 OIDC Discovery), PKCE(S256), 토큰 대상 지정(RFC 8707의 `resource`)을 갖춰야 합니다. 클라이언트 등록은 Client ID Metadata Document(CIMD, 클라이언트 id가 곧 메타데이터 문서의 HTTPS 주소)를 권하고, 동적 등록(DCR)은 폐기 예정입니다. 사용자와 그룹의 원본은 위키입니다(ADR-08).

| 선택지 | CIMD | 토큰 대상 지정 | 사용자 | 걸리는 점 |
|---|---|---|---|---|
| Keycloak 26.7 | 실험 기능 | 지원하지 않음(공식 MCP 문서) | 별도 저장소, 위키와 동기화 | 메모리 최소 750MB, 권장 2GB. 서버의 남은 여유가 약 2GB |
| 관리형(Auth0, WorkOS 등) | 지원 | 업체마다 다름 | 업체로 옮김 | 유료, 외부 의존 |
| 별도 Spring 인가 서버 앱 | 직접 구현 | 직접 구현 | 위키 API로 확인 | JVM이 하나 늘고, 비밀번호 확인 API를 위키에 새로 열어야 함 |
| **위키 서비스 안의 Spring 인가 서버 (선택)** | 직접 구현 | 직접 구현 | 위키 사용자 그대로 | 위키 서비스가 인가 서버를 겸함 |

- **결정**:
  - Spring Security 7.1의 인가 서버를 위키 서비스에 넣습니다. 토큰의 사용자(`sub`)가 곧 위키 사용자 id입니다.
  - 외부 클라이언트(Claude 등)는 CIMD로 받습니다. 인가 서버 메타데이터에 `client_id_metadata_document_supported: true`와, `token_endpoint_auth_methods_supported`의 `none`을 함께 알립니다. Claude는 둘 다 있어야 CIMD를 씁니다.
  - 우리가 만든 클라이언트(데모 에이전트, 부하 테스트, 점검 도구)는 미리 등록합니다. 사용자 기기에서 도는 것은 공개 클라이언트, 서버에서 도는 것은 비밀로 인증하는 기밀 클라이언트입니다. DCR은 열지 않습니다.
  - 토큰의 대상(`aud`)에는 요청의 `resource`가 등록된 MCP 서버 주소와 같을 때만 그 주소를 넣고, 다르거나 없으면 발급하지 않습니다. MCP 서버는 서명, 발급자, 만료, 대상을 모두 검증합니다.
  - 클라이언트 신뢰 등급(ADR-17)은 인가 서버가 정해 토큰에 넣습니다. 사내 등급은 비밀로 인증하는 기밀 사전 등록 클라이언트만 받을 수 있고, 공개 클라이언트를 사내로 설정하면 위키가 뜨지 않습니다. CIMD와 공개 클라이언트는 모두 외부입니다. MCP 서버는 서명된 토큰의 등급만 읽습니다.
  - 동의는 기밀 클라이언트에만 기억합니다. 공개 클라이언트(CIMD 포함)는 이전에 허용했어도 새 인가마다 동의 화면을 보여 줍니다(RFC 8252 8.6). 공개 클라이언트의 id는 누구나 쓸 수 있어, 동의를 기억하면 로그인 세션이 살아 있는 동안 같은 id를 쓴 다른 프로그램이 화면 없이 코드를 받아 갑니다. 처음에는 모든 클라이언트의 동의를 기억했다가, 배포 뒤 Claude Code로 붙여 보면서 저장된 동의 때문에 동의 화면이 나오지 않는 것을 보고 바꿨습니다.
- **결정 이유**:
  - 사용자와 그룹의 원본이 위키라, 동기화 없이 같은 id를 씁니다. 서버 한 대의 메모리 제약(ADR-23) 안에서 프로세스도 늘지 않습니다.
  - 어느 후보를 골라도 CIMD와 대상 지정 중 하나 이상은 직접 메워야 합니다. 그렇다면 같은 코드베이스에서 테스트로 보증하는 쪽이 낫습니다(ADR-03과 같은 원칙).
  - DCR을 열지 않는 이유: 명세에서 폐기 예정이고, Claude는 새로 연결할 때마다 클라이언트를 새로 등록해 등록이 끝없이 쌓입니다. 클라이언트 id도 매번 바뀌어 ADR-17의 등급을 id에 묶을 수 없습니다.
  - 등급을 인가 서버가 정하는 이유: 공개 클라이언트의 id는 비밀이 아니어서(저장소에도 공개됨) 다른 앱이 같은 id로 인가 흐름을 시작하는 것을 막을 수 없습니다(RFC 8252 8.6). 사용자가 동의만 하면 그 앱이 사내 등급 토큰을 받습니다. 클라이언트가 비밀로 인증했는지 아는 곳은 인가 서버뿐이라, 등급 규칙을 거기 한 곳에 두어야 두 서비스의 설정이 어긋나 새는 일이 없습니다. 처음에는 MCP 서버 설정의 목록으로 정했다가 보안 검토에서 이 빈틈이 드러나 바꿨습니다.
- **감수한 비용**:
  - CIMD 검증과 대상 지정을 직접 구현합니다. 허술하면 다른 앱을 사칭하는 메타데이터, 내부망 주소로 메타데이터를 가져오게 하는 요청 위조(SSRF), 다른 서비스용 토큰의 재사용이 생깁니다. 그래서 메타데이터는 공인 주소의 HTTPS에서만 크기와 시간 제한을 두고 가져오고, 문서 안의 `client_id`가 가져온 주소와 같아야 하며, 돌아갈 주소(`redirect_uri`)는 문서에 적힌 것과 정확히 같아야 합니다. 동의 화면에는 문서가 주장하는 앱 이름보다 `client_id`의 도메인을 앞세웁니다. 이 경우들은 권한·등급 테스트셋처럼 테스트로 둡니다.
  - CIMD 문서를 가져오는 일은 누구나 로그인 없이 일으킬 수 있어, 느린 서버로 위키의 요청 스레드를 붙잡아 위키 전체를 멈추게 할 수 있습니다(보안 검토에서 재현). 그래서 이름 해석부터 응답까지 전체 시간을 넘기면 연결을 끊고, 동시에 가져오는 수에 상한을 두며, 실패한 주소는 잠시 다시 가져오지 않습니다.
  - 공개 클라이언트의 갱신 토큰은 쓸 때마다 바꾸고, 이미 바뀐 토큰이 다시 들어오면 탈취로 보고 그 인가 전체를 무효로 합니다. 갱신을 이어 가도 처음 로그인에서 30일이 지나면 다시 로그인해야 합니다. 이를 위해 인가 기록을 위키 DB에 둡니다.
  - 위키 서비스가 인가 서버를 겸해, 위키가 멈추면 새 로그인도 멈춥니다. 다만 위키가 멈추면 그룹 캐시(60초)가 끝난 뒤 검색도 이미 멈추므로(ADR-08) 새로 생기는 장애 지점은 아닙니다.
  - 위키에 비밀번호 로그인이 생깁니다. 가상 회사라 사내 SSO가 없기 때문입니다.
  - DCR만 지원하는 클라이언트는 사전 등록해야 붙습니다.
- **재검토 조건**: 실제 회사 SSO(Okta, Entra ID 등)에 붙여야 하면 인가 서버를 위키에서 빼고, 위키는 SSO 사용자를 위키 사용자에 대응시키는 역할만 합니다. Spring Security가 CIMD나 RFC 8707을 정식으로 지원하면 직접 구현한 부분을 그것으로 바꿉니다.
