# ADR-25. 쿼리 임베딩은 묶어서 bf16으로 하고, 지연 예산은 리랭커 몫을 옮겨 다시 나눔

- 상태: 확정 (M5 부하 측정 뒤)
- 주요 대안: 작은 모델(multilingual-e5-base)로 교체, 인스턴스 증설
- 출처: 설계서 8. 운영과 성능

M5 부하 측정(`experiments/m5-load`)에서 동시 50의 `search_wiki` p95가 20.5초였습니다. 병목은 물리 코어 하나에서 요청마다 따로 도는 쿼리 임베딩이었고(처리량 초당 약 3.3건), ADR-23의 재검토 조건에 해당했습니다. 개선마다 판정 기준을 측정 전에 적고 하나씩 쟀습니다(`experiments/m5-speedup`).

| 선택지 | 잰 결과 | 판정 |
|---|---|---|
| **쿼리 묶음 처리 (선택)** | 동시 50 처리량 2.72배, 벡터 같음(코사인 0.9999998), 혼자일 때 p95 +5ms | 채택 |
| **쿼리만 bf16 (선택)** | 골든셋 Recall@5 0.970으로 같음(결과가 다른 문항 0개), 쿼리 인코딩 p50 250ms에서 101ms | 채택 (ADR-11 재판정) |
| PyTorch 스레드 2개 | 서버 벤치마크에서 bf16 32개 묶음 처리량이 초당 54건에서 31건으로 줄어듦 | 기각 |
| 검색 저장소 연결 풀 | 동시 50에서 벡터 검색 p95 −22%, 전체 p95 −4.3% (기준: 절반, 10%) | 기각 |
| multilingual-e5-base로 교체 (ADR-11의 교체 규칙) | 재지 않음. 품질이 약 2%p 낮고 전체 재색인이 필요 | 하지 않음 |
| 인스턴스 증설 | 재지 않음. 크레딧 소모가 빨라짐 | 하지 않음 |

- **결정**:
  - 검색 서버의 쿼리 임베딩은 전용 스레드 하나가 묶어서 합니다. 한 묶음을 인코딩하는 동안 들어온 쿼리를 다음 묶음으로 모으고(최대 32개), 기다리는 창은 두지 않습니다.
  - 배포 서버에서는 쿼리만 bf16으로 인코딩합니다(`WIKI_QUERY_DTYPE`). 기본값과 문서 벡터는 float32 그대로라 재색인하지 않습니다. bf16은 AMX가 있는 배포 서버에서 2.5배 빠르지만, 개발용 맥(M1 GPU)에서는 쿼리 하나가 36ms에서 80ms로 오히려 느려져 배포 설정에서만 켭니다.
  - 8장 지연 예산에서 리랭킹 몫(450ms)을 쿼리 임베딩으로 옮겨 쿼리 임베딩 예산을 550ms로 둡니다. 리랭커는 M2 판정으로 도입하지 않아 이 몫이 비어 있었고, 합계(750ms)는 그대로입니다. ADR-11의 "쿼리 임베딩이 예산을 넘으면 multilingual-e5-base로 바꾼다"는 규칙은 이 결정으로 대체합니다. **이 예산 조정은 부하 측정 결과를 본 뒤 내린 결정입니다.**
  - 동시 50의 p95 목표(800ms)는 이 서버에서 맞추지 못한 채로 둡니다.
- **결정 이유**:
  - 채택한 두 변경은 검색 결과를 바꾸지 않았고(골든셋 결과 같음) 비용도 들지 않습니다.
  - e5-base는 모든 요청의 검색 품질을 낮춥니다. 정확성이 성능보다 먼저라는 원칙(0장)에 따라, 동시 50에서의 지연을 위해 품질을 깎지 않습니다. 평상시인 동시 10은 p95 506ms로 목표 안이고, 동시 50에서도 오류율은 0%입니다.
  - 이 서버는 물리 코어 하나가 쿼리 임베딩으로 차 있습니다(스레드 2개 실험). 동시 50에서 p95 800ms에 필요한 처리량(초당 약 60건)은 지금(33건)의 약 두 배라, 소프트웨어로 더 짜낼 여지가 작습니다.
- **감수한 비용**:
  - 동시 50에서 p95가 2,263ms로 1장 목표(800ms)를 넘습니다. 지연의 대부분은 묶음 차례를 기다리는 시간입니다.
  - 지연 예산을 결과를 본 뒤 다시 나눴습니다. 처음 예산은 8장 표에 함께 남깁니다.
  - 쿼리와 문서 벡터의 형식이 다릅니다. 판정에서 검색 결과가 같았지만, 모델이나 라이브러리를 바꾸면 다시 판정합니다. CI의 골든셋 회귀 검사는 float32 쿼리로 돕니다(CI 러너에는 bf16 가속이 없음).
- **재검토 조건**: 실사용에서 동시 요청이 평상시(10)를 자주 넘거나 장기 호스팅처를 정할 때(ADR-23), 물리 코어 2개 이상에서 같은 방법으로 다시 잽니다. 쿼리 임베딩 캐시(8장 "캐싱 결정")는 실사용 로그로 반복 질의 비율을 확인한 뒤 검토합니다.
