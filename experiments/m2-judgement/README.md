# M2 판정 실험 (ADR-02·11·12·13, ADR-20)

이 문서의 "실험 계획" 절은 첫 실험 전에 쓰고 골든셋과 함께 git 태그 `golden-v1`로 고정합니다. 결과를 본 뒤 계획을 바꾸지 않습니다(ADR-20). 결과는 실험이 끝난 뒤 "결과" 절에 덧붙입니다.

## 실험 계획

### 골든셋

- `data/golden/golden.jsonl`, 300문항. 사실 조회 90, 절차 60, 약어·고유명사 45, 최신성 30, 권한 제한 30, 모순·개정 15, 답 없음 30.
- 만든 방법은 `data/golden/README.md`에 있습니다. 질문은 gpt-5.4가 쓰고, 정답 라벨은 출처를 모르는 다른 모델이 따로 붙인 뒤 출처와 비교했습니다(ADR-14).
- 문항마다 질문자(가상 사용자)가 있고, 모든 구성은 그 사용자의 권한 pre-filter를 켠 채 검색합니다.

### 지표

`src/wiki_rag_mcp/evaluation/metrics.py`에 정의가 있습니다. 결과는 search_wiki가 돌려주는 청크 순서 그대로이고, 청크의 문서가 정답이면 관련 있는 결과로 봅니다.

- Recall@5: 상위 5개 결과의 문서 가운데 정답 문서가 하나라도 있으면 1
- MRR@10: 정답 문서가 처음 나온 결과 순위의 역수
- nDCG@10: 관련도 0 또는 1, 같은 문서는 처음 나올 때만 셈
- 정답이 있는 270문항으로 계산하고, 답 없음 30문항은 1위 점수만 기록합니다.

### 구성 (`src/wiki_rag_mcp/evaluation/run.py`)

| 이름 | 인덱스 | 검색 | 리랭커 |
|---|---|---|---|
| baseline | bge-m3, 맥락 헤더 | 벡터 | - |
| no-header | bge-m3, 헤더 없음 | 벡터 | - |
| hybrid | bge-m3, 맥락 헤더 | BM25 + 벡터, RRF(k=60, 각 후보 50개) | - |
| vector-rerank / hybrid-rerank | bge-m3, 맥락 헤더 | 앞 판정으로 정한 쪽 | bge-reranker-v2-m3, 후보 30개 |
| gemini-vector / gemini-hybrid | gemini-embedding-001, 맥락 헤더 | 앞 판정으로 정한 쪽 | - |

고정한 검색 설정:
- 형태소 분석기: nori(`nori_tokenizer` + `nori_part_of_speech` + `lowercase`)
- 동의어 사전: 쓰지 않음
- BM25 필드: `title`, `text`(같은 가중치)
- RRF: k=60, 후보는 BM25와 벡터 검색에서 각각 50개
- 리랭커: 후보 30개, 입력 상한 512토큰, 입력 형식 "제목 > 섹션 경로" + 본문
- 청크: 300~500토큰, 12% 겹침, 표·코드 블록 보존

모델 버전:
- bge-m3: 커밋 5617a9f6, float32
- bge-reranker-v2-m3: 커밋 953dc6f6, float32
- gemini-embedding-001: API라 버전을 고정할 수 없어 측정 날짜를 함께 적음

### 판정 순서와 기준

각 행은 그 위 행까지의 판정을 반영한 구성에 해당 요소만 더해 비교합니다(7장).

1. **맥락 헤더**
   - 비교: `no-header` 대 `baseline`, Recall@5
   - 헤더를 뺄 때: 차이(헤더 있음 − 없음)의 신뢰구간 상한이 0보다 작을 때만
   - 헤더를 빼면 이후 행은 헤더 없는 인덱스로 돌립니다.
2. **하이브리드 (ADR-02, ADR-12)**
   - 비교: 1번 결과 구성 대 그 구성 + 하이브리드, Recall@5, 기준값 +2%p
   - 채택이면 OpenSearch와 RRF를 유지합니다.
   - 기각·보류면 PostgreSQL + pgvector로 단순화합니다(ADR-02 "단순화할 때").
3. **리랭커 (ADR-13)**
   - 비교: 2번 결과 구성 대 그 구성 + 리랭커, MRR@10, 기준값 +0.05
   - 지연 조건: 리랭킹 단계 p95 450ms 이내
   - 채택 조건: MRR@10과 지연 두 조건을 모두 만족해야 합니다.
4. **상용 임베딩 (ADR-11)**
   - 비교: 2번 결과 구성 대 임베딩만 gemini로 바꾼 구성, Recall@5, 기준값 +5%p
   - 채택이면 상용 API 전환을 재검토하고, 보류·기각이면 로컬 모델을 유지합니다.

판정 규칙(`src/wiki_rag_mcp/evaluation/judge.py`):
- 문항을 복원 추출하는 퍼센타일 부트스트랩을 10,000회, 시드 20260927로 돌립니다.
- 채택: 신뢰구간 하한 > 0 이고 측정한 차이 ≥ 기준값
- 기각: 신뢰구간 상한 < 기준값
- 보류: 그 밖

### 측정 환경

- 장비: Apple M1 Pro, 10코어, 메모리 16GB
- 질문 임베딩과 리랭커는 CPU에서 돌립니다. 배포 서버에 GPU가 없기 때문입니다. 문서 임베딩은 결과가 같아 MPS로 했습니다.
- 모든 구성은 첫 10문항으로 워밍업한 뒤 잽니다. 리랭커 구성은 300문항을 3회 순차 실행해 리랭킹 단계 p95를 구하고, 품질 지표는 첫 회로 계산합니다.
- OpenSearch 3.8.0 단일 노드(Docker, JVM 힙 1GB)

### 함께 보고할 것 (판정에 쓰지 않음)

- 유형별 Recall@5
- nDCG@10
- 질문과 정답 문서의 단어 겹침 비율(ADR-14): 질문이 문서 표현을 닮아 키워드 검색에 유리했는지 보기 위한 값
- 두 구성의 결과가 다른 문항 비율(ADR-20의 시뮬레이션 가정과 비교)

## 결과

골든셋 `golden-v1`(커밋 eb191a9)로 2026-09-27에 쟀습니다. 모든 수치는 정답이 있는 270문항 기준이고, 괄호 안은 차이의 95% 신뢰구간입니다.

### 1. 맥락 헤더: 유지

| 구성 | Recall@5 | MRR@10 | nDCG@10 | p95 |
|---|---|---|---|---|
| baseline (헤더 있음) | 0.970 | 0.910 | 0.924 | 106ms |
| no-header | 0.967 | 0.909 | 0.923 | 104ms |

- Recall@5 차이(헤더 있음 − 없음): +0.4%p (−0.7 ~ +1.9). 두 구성의 결과가 다른 문항은 1.1%였습니다.
- 헤더를 빼는 조건(신뢰구간 상한 < 0)에 해당하지 않아 헤더를 유지합니다.
- 효과가 있다고도 말할 수 없습니다. 헤더는 비용이 들지 않아 기본값으로 둔 것이고(6장), 개선으로 주장하지 않습니다.

### 2. 하이브리드 (ADR-02, ADR-12): 보류, 도입하지 않고 저장소를 단순화

| 구성 | Recall@5 | MRR@10 | nDCG@10 | p95 |
|---|---|---|---|---|
| baseline (벡터) | 0.970 | 0.910 | 0.924 | 106ms |
| hybrid (BM25 + 벡터, RRF) | 0.985 | 0.911 | 0.927 | 106ms |

- Recall@5 차이: +1.5%p (−0.4 ~ +3.7), 기준값 +2%p, 판정 **보류**
- MRR@10 차이: +0.1%p (−2.0 ~ +2.3), nDCG@10 차이: +0.3%p (−1.4 ~ +2.1) (기록만)
- 결과가 다른 문항은 8개(3.0%)로, 하이브리드가 6문항에서 이기고 2문항에서 졌습니다.
- **약어·고유명사 45문항에서는 두 구성의 결과가 하나도 다르지 않았습니다.** ADR-02는 "에러 코드처럼 정확히 일치해야 하는 질문이 많아 키워드 검색이 필요하다"는 가설에서 출발했지만, 이 골든셋에서는 bge-m3가 PRJ-204, SP-E2003 같은 코드도 이미 찾았습니다. 하이브리드가 이긴 6문항은 사실 조회와 절차 질문이었습니다.
- 실험 전에 정한 규칙대로, 보류이므로 구성 요소를 늘리지 않습니다. OpenSearch를 PostgreSQL + pgvector로 옮기고 벡터 검색만 씁니다(ADR-02 "단순화할 때").
- 한계:
  - 기준선이 이미 0.970이라 개선 여지가 3%p뿐이었습니다(천장 효과).
  - 두 구성의 결과가 다른 문항은 3.0%로, ADR-20 시뮬레이션이 가정한 10~15%보다 훨씬 적었습니다.
  - 실사용 질문이 이 골든셋보다 어렵다면 판정이 달라질 수 있습니다. ADR-20의 재검토 조건(실사용 질문 로그로 골든셋 재구성)이 이 경우입니다.

- 설계서 6장의 "점수가 비슷하면 최근 수정 문서를 우선한다"는 M1에서 구현하지 않았습니다.
- 결과마다 수정일과 "오래된 문서" 표시가 붙어 클라이언트 LLM이 판단할 근거는 있지만, 검색 순위만으로는 옛 문서가 3분의 1에서 위에 옵니다.
- 이 결과를 본 뒤 바로 최근 문서 우선을 넣지 않습니다. 판정 기준을 먼저 적고 별도 실험으로 결정합니다.

### 답 없음 문항 (기록만)

1위 결과의 점수 중앙값은 정답이 있는 문항 0.834, 답 없음 문항 0.765입니다(baseline, OpenSearch 점수 = (1 + 코사인 유사도) / 2). 점수 차가 작아 점수 문턱으로 "근거 없음"을 가리기는 어렵습니다. 지금처럼 결과를 돌려주고 클라이언트 LLM이 관련성을 판단하게 둡니다(ADR-04).

### 3. 리랭커 (ADR-13): 도입하지 않음

하이브리드가 보류로 나와, 계획대로 벡터 검색 위에 리랭커를 얹어 비교했습니다.

| 구성 | Recall@5 | MRR@10 | nDCG@10 | 전체 p95 | 리랭킹 단계 p95 |
|---|---|---|---|---|---|
| baseline (벡터) | 0.970 | 0.910 | 0.924 | 106ms | - |
| vector-rerank | 0.985 | 0.956 | 0.962 | 7,402ms | 7,280ms |

- **MRR@10**
  - 차이: +0.046 (+0.021 ~ +0.071), 기준값 +0.05, 판정 **보류**
  - 신뢰구간 하한이 0보다 커서 순위가 좋아진 것은 확실하지만, 실험 전에 정한 "의미 있는 크기"에는 조금 못 미쳤습니다.
- **리랭킹 단계 p95**
  - 7,280ms로 예산(450ms)의 16배입니다.
  - 3회 측정이 각각 7,234 / 7,402 / 7,201ms였고, p50은 5,742ms, 최대는 8,991ms입니다.
- **결론**: 두 조건을 모두 넘어야 켜는데 둘 다 넘지 못해 도입하지 않습니다.
- **느린 이유**
  - 질문 하나마다 후보 30개와 질문을 한 쌍씩(합계 1만 1천~1만 5천 토큰) 5.6억 파라미터 모델에 넣습니다. 30쌍은 한 번에 배치로 추론했고, CPU를 300~360% 썼습니다. 루프나 모델 재로드 문제가 아니라 계산량 자체가 큽니다.
- **후속 과제**
  - 양자화(ONNX int8)한 다국어 소형 리랭커와 후보 축소(10~20개)는 효과가 있어 보입니다.
  - 다만 예산에 들어오려면 13배 이상 빨라져야 합니다. 판정 기준을 먼저 적은 뒤 별도 실험으로 다룹니다.
- **측정 절차 개선점**
  - 품질은 한 번만 재고 지연만 여러 번 재면 측정 시간이 크게 줄어듭니다. 이번에는 계획대로 3회를 모두 돌렸습니다(약 1시간 40분).
  - 측정 스크립트에 진행률 표시가 없었습니다. 다음 실험 전에 넣습니다.

### PostgreSQL + pgvector로 옮긴 뒤 재측정 (ADR-02 "단순화할 때", ADR-22)

| 구성 | Recall@5 | MRR@10 | nDCG@10 | 전체 p95 | 검색 단계 p95 |
|---|---|---|---|---|---|
| baseline (OpenSearch 벡터) | 0.970 | 0.910 | 0.924 | 106ms | 3.2ms |
| pg-vector (pgvector 0.8.6, HNSW m=16, ef_construction=128, iterative scan strict_order) | 0.970 | 0.910 | 0.924 | 109ms | 6.7ms |

- 270문항의 결과가 모두 같았습니다(결과가 다른 문항 0%). "OpenSearch 벡터 검색보다 확실히 낮으면 조정한다"는 조건에 해당하지 않아 이전을 확정합니다.
- 권한 테스트셋과 결과 수 테스트를 두 저장소에서 모두 통과했습니다. 문서 제한 조건을 일부러 빼면 테스트가 실패하는 것도 확인했습니다.
- 서버, 색인, 테스트의 기본 저장소를 pgvector로 바꿨습니다. OpenSearch 코드와 컨테이너는 상용 임베딩 비교가 끝나면 지웁니다. pgvector의 HNSW는 2,000차원까지만 지원해, 3,072차원인 gemini-embedding-001 비교는 기준선과 같은 OpenSearch에서 합니다.

### 4. 상용 임베딩 (ADR-11): 기각, 로컬 모델 유지

하이브리드가 보류로 나와, 계획대로 리랭커를 넣기 전의 벡터 검색에서 임베딩 모델만 바꿔 비교했습니다. pgvector의 HNSW는 2,000차원까지만 지원해, 3,072차원인 gemini-embedding-001은 기준선과 같은 OpenSearch(lucene HNSW, 같은 매개변수)에서 쟀습니다.

| 구성 | Recall@5 | MRR@10 | nDCG@10 |
|---|---|---|---|
| baseline (bge-m3, 로컬) | 0.970 | 0.910 | 0.924 |
| gemini-vector (gemini-embedding-001, 3,072차원) | 0.981 | 0.921 | 0.934 |

- Recall@5 차이: +1.1%p (−1.5 ~ +3.7), 기준값 +5%p, 판정 **기각**. 신뢰구간 상한도 기준값에 못 미쳐, 상용 API가 5%p 넘게 낫다는 가능성은 배제됩니다.
- MRR@10 +1.1%p (−1.8 ~ +4.1), nDCG@10 +0.9%p (−1.4 ~ +3.3) (기록만)
- 결과가 다른 문항은 Recall@5 기준 4.1%(11문항)였습니다.
- 로컬 모델(bge-m3)을 유지합니다. ADR-11이 로컬 모델을 고른 이유(전체 문서를 새 외부 업체로 보내지 않음, 비용 없음, 버전 고정)를 이 골든셋에서는 품질 손해 없이 지킬 수 있습니다.
- 측정 조건:
  - 문서는 RETRIEVAL_DOCUMENT, 질문은 RETRIEVAL_QUERY 작업 유형으로 임베딩했습니다(2026-09-27~28, API라 버전을 고정할 수 없음).
  - 질문 임베딩은 미리 받아 캐시에서 읽어, 지연(p95 4ms)은 bge-m3와 비교할 수 없습니다.
  - 무료 등급의 하루 한도(요청 1,000건)에 걸려 두 번에 나눠 받았습니다.

|---|---|---|---|

| ADR-02, ADR-12 하이브리드 | Recall@5 +2%p | +1.5%p (−0.4 ~ +3.7), 보류 | 도입하지 않고 pgvector로 단순화 (ADR-22) |
| ADR-13 리랭커 | MRR@10 +0.05, 리랭킹 p95 450ms | +0.046 (+0.021 ~ +0.071) 보류, p95 7,280ms | 도입하지 않음 |
| ADR-11 상용 임베딩 | Recall@5 +5%p | +1.1%p (−1.5 ~ +3.7), 기각 | 로컬 모델 유지 |

네 판정 모두 구성 요소를 늘리지 않는 쪽으로 끝났습니다. 측정값만 보면 하이브리드, 리랭커, 상용 임베딩 모두 기준선보다 조금씩 높았지만, 실험 전에 정한 기준을 넘는 효과로 증명되지는 않았습니다.

공통 한계:
- 기준선 Recall@5가 이미 0.970이라 개선 여지가 3%p뿐이었습니다(천장 효과).
- 질문 작성자가 핵심 사실을 보고 질문을 써서, 실제 직원 질문보다 쉬울 수 있습니다.
- 실사용 질문 로그로 골든셋을 다시 만들면 같은 규칙으로 네 결정을 다시 판정합니다(ADR-20 재검토 조건).
