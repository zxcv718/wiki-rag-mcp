# M3 인덱싱 측정

아웃박스와 증분 색인(ADR-09, ADR-10, ADR-19)이 설계서의 목표를 지키는지 잽니다. 판정 실험(ADR-20)이 아니라, 1장과 5장에 적힌 목표치와 비교하는 측정입니다.

| 측정 | 목표 | 스크립트 | 결과 |
|---|---|---|---|
| 임베딩 절감률 | 목표치 없음. ADR-10 검증 방법대로 기록 | `savings.py` | `results/savings.jsonl` |
| 문서 수정 후 검색 반영까지 걸린 시간 | p95 30초 이하 (1장) | `latency.py` | `results/latency.jsonl`, `results/latency_summary.json` |

## 임베딩 절감률 (ADR-10)

가상 위키 200문서 각각에 수정 시나리오를 한 번씩 적용하고, 증분 색인이 새로 임베딩한 청크 수를 그 문서를 통째로 다시 임베딩할 때의 청크 수와 비교했습니다. 임베딩 호출 수는 모델과 관계없으므로 가짜 인코더로 셌고, 청크 분할은 실제 토크나이저(bge-m3)를 썼습니다.

```bash
uv run python experiments/m3-indexing/savings.py
```

| 시나리오 | 새로 임베딩한 청크 | 문서 전체 재임베딩 | 절감 |
|---|---|---|---|
| 섹션 하나 끝에 문장 추가 | 200 | 1,151 | 82.6% |
| 문서 끝에 섹션 추가 | 200 | 1,151 | 82.6% |
| 문서 제한 변경 | 0 | 1,151 | 100% |
| 문서 등급 변경 | 0 | 1,151 | 100% |
| 제목 변경 (본문 첫 줄 제목도 함께) | 1,151 | 1,151 | 0% |

- 섹션 하나를 고치면 그 섹션의 청크만 다시 임베딩합니다. 이 코퍼스는 섹션 1,148개 중 1,145개가 청크 하나라서, 절감률은 문서당 섹션 수(평균 5.75개)로 거의 정해집니다. 긴 섹션이 청크 여러 개로 나뉘는 위키에서는 섹션 안 한 곳만 고쳐도 그 섹션의 청크가 모두 바뀌어 절감률이 낮아집니다.
- 권한·등급 변경은 권한 필드만 고치고 임베딩하지 않습니다(4장 "권한 변경 전파"의 핵심).
- 제목은 모든 청크의 맥락 헤더("스페이스 > 문서 제목 > 섹션 경로")에 들어가서, 바뀌면 문서 전체를 다시 임베딩합니다. 청크 id는 그대로지만 임베딩 입력이 바뀌기 때문입니다.
- 코퍼스 전체를 다시 색인하는 방식과 비교하면, 섹션 하나를 고칠 때 1,151개 대신 1개를 임베딩합니다.

## 문서 수정 후 검색 반영까지 걸린 시간

위키 관리자 API로 문서를 바꾸고, 응답을 받은 시각부터 검색 DB의 문서 상태(`doc_state`)에 새 revision이 기록될 때까지를 쟀습니다. 상태는 청크 교체와 같은 트랜잭션의 마지막에 쓰이므로, 기록된 순간부터 검색 결과에 반영돼 있습니다. 수정한 직후 동료가 검색하는 상황과 같은 구간입니다.

```bash
docker compose up -d && uv run wiki-rag-seed
uv run wiki-rag-worker     # 다른 터미널에서, 실제 bge-m3로
uv run python experiments/m3-indexing/latency.py
```

- 환경: Apple M1 Pro 노트북 한 대에서 위키 서비스·위키 DB·Redis·검색 DB를 Docker로, 워커를 로컬 Python(bge-m3, MPS, float32)으로 돌렸습니다. 워커는 하나이고 파티션 4개를 모두 맡았습니다.
- 시드 문서 200개는 건드리지 않도록 측정용 문서를 만들어 쓰고 마지막에 지웠습니다. 스페이스 권한 변경만 시드 문서에 닿는데, 권한을 바꿨다가 원래대로 되돌렸습니다. 측정 뒤 `wiki-rag-reconcile --dry-run`으로 위키와 인덱스가 어긋난 문서가 없는 것을 확인했습니다(260문서, 0건).

| 시나리오 | 건수 | p50 | p95 | 최대 |
|---|---|---|---|---|
| 새 문서 (1초 간격) | 20 | 0.69초 | 1.06초 | 1.61초 |
| 섹션 하나 수정 (1초 간격) | 20 | 0.48초 | 0.54초 | 0.57초 |
| 문서 제한 변경 | 20 | 0.47초 | 0.51초 | 0.68초 |
| 문서 등급 변경 | 20 | 0.47초 | 0.52초 | 0.53초 |
| 문서 삭제 | 20 | 0.47초 | 0.52초 | 0.52초 |
| 새 문서 20개를 한꺼번에 | 20 | 5.30초 | 8.05초 | 8.35초 |
| 스페이스 권한 변경 (문서 34개, 2회) | 68 | 0.56초 | 0.87초 | 0.93초 |
| 전체 | 188 | 0.50초 | 5.52초 | 8.35초 |

- 모든 시나리오가 목표(p95 30초)보다 짧습니다.
- 임베딩이 없거나 적은 변경은 0.5초 안팎이고, 대부분이 아웃박스 폴링 간격(0.5초)입니다. 폴러가 앞 주기를 마치고 0.5초를 쉬므로, 이벤트는 평균 0.25초쯤 기다렸다가 나갑니다.
- 가장 느린 경우는 새 문서가 한꺼번에 들어올 때입니다. 워커 하나가 문서를 차례로 임베딩해서, 뒤에 선 문서가 앞 문서들의 임베딩을 기다립니다. 문서 하나(청크 약 6개)에 0.4초쯤 걸려서, 새 문서가 70여 개 넘게 한꺼번에 들어오면 마지막 문서는 30초를 넘길 것으로 봅니다. 대량 이관이 이런 경우인데, 그때는 `wiki-rag-index --source wiki`로 한 번에 색인하거나 워커를 파티션별로 나눠 다른 장비에서 돌립니다.
- 스페이스 권한 변경은 문서 34개에 이벤트가 한꺼번에 나가지만, 임베딩 없이 권한 필드만 고쳐 1초 안에 끝납니다.

### 한계

- 워커가 10분쯤 쉬다가 받은 첫 새 문서는 반영까지 9.0초가 걸렸습니다(위키를 읽은 뒤 청크 1개 임베딩에 8.2초). 바로 이어 보낸 같은 요청 세 번은 0.55~0.87초였습니다. 메모리 16GB 노트북에서 Docker와 빌드가 메모리를 많이 쓰는 동안 모델 가중치(약 2.2GB)가 스왑으로 밀려났다가 다시 올라온 것으로 봅니다. 목표 안이지만, 수정이 드물게 들어오는 실제 사용에서는 이런 첫 요청이 자주 생길 수 있어 배포 서버에서 다시 봅니다.
- 노트북 한 대에서, 검색 요청이 없는 상태로 쟀습니다. 검색과 인덱싱이 같은 장비의 CPU·GPU를 나눠 쓰면 더 느려집니다. 배포 서버에서 검색 부하와 함께 다시 재는 것은 M5(부하 테스트)에서 합니다.
- 처음 적재(시드 200문서)는 M2 때 같은 내용으로 색인한 청크가 있어 임베딩 1,151개를 모두 다시 썼습니다(새 임베딩 0개). 그래서 처음 적재 시간은 측정값으로 쓰지 않았습니다.
