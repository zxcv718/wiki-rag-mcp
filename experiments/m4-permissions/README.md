# M4 권한 회수 측정

검색 서버를 위키 API에 연결한 뒤(4장 "구현 세부 (M4)"), 권한을 회수하면 검색에서 얼마나 빨리 사라지는지와 그룹 해석에 걸리는 시간을 잽니다. 판정 실험(ADR-20)이 아니라 1장과 8장의 목표치와 비교하는 측정입니다.

| 측정 | 목표 | 결과 |
|---|---|---|
| 권한 회수 후 검색에서 사라질 때까지 | 30초 이하 (1장, 4장 "검증 방법") | 문서 제한 변경 p95 0.42초, 그룹 제거 p95 0.40초 |
| 회수 직후 본문(`get_document`) 차단 | 즉시 (ADR-07 본문 재확인) | 40번 중 40번 |
| 그룹 해석 (인증·권한 해석 예산) | 20ms 이하 (8장) | 캐시 적중 p95 0.37ms, 위키 호출 p95 4.45ms |

```bash
docker compose up -d && uv run wiki-rag-seed
uv run wiki-rag-worker     # 다른 터미널에서, 실제 bge-m3로
uv run python experiments/m4-permissions/revocation.py
```

## 방법

- 서버와 같은 구성으로 MCP 도구를 부릅니다. 위키는 Spring 위키 API, 그룹은 Redis 캐시, 검색은 실제 인덱스(`wiki-chunks`)와 bge-m3입니다.
- 측정용 사용자를 새로 만들어 `eng` 그룹에 넣고, `engineering` 스페이스(eng 그룹만 봄)에 측정용 문서를 만들어 검색에 나올 때까지 기다린 뒤 권한을 회수합니다. 관리자 API의 응답을 받은 시각부터 `search_wiki` 결과(상위 5개)에서 그 문서가 사라질 때까지를 50ms 간격으로 확인합니다. 회수 직후 `get_document`도 한 번 부릅니다.
- 문서 제한 변경은 제한을 `group:dba`로 바꿉니다. 위키, 아웃박스, Redis Streams, 인덱서(권한 필드만 고침)를 거칩니다.
- 그룹 제거는 사용자를 `eng` 그룹에서 뺍니다. 인덱스는 그대로이고, 워커가 멤버십 이벤트를 받아 그룹 캐시를 무효화합니다. 제거하기 직전의 검색으로 그룹이 캐시에 올라가 있는 상태에서 잽니다. 잰 뒤 다시 넣고 다시 보이기까지도 잽니다.
- 같은 질의를 반복해서 보내므로 질의 임베딩은 한 번만 계산해 둡니다. 잴 것은 권한 반영이고, 검색과 권한 필터는 매번 실제로 돕니다.
- 그룹 해석은 캐시를 무효화한 뒤 한 번(위키 호출), 곧바로 한 번 더(캐시 적중) 부르기를 200번 반복했습니다.
- 환경: Apple M1 Pro 노트북 한 대에서 위키 서비스, 위키 DB, Redis, 검색 DB를 Docker로, 워커와 측정 스크립트를 로컬 Python으로 돌렸습니다. 결과는 `results/`에 있습니다.

## 결과

| 시나리오 | 건수 | p50 | p95 | 최대 | 회수 직후 본문 차단 |
|---|---|---|---|---|---|
| 문서 제한 변경 | 20 | 0.36초 | 0.42초 | 0.45초 | 20/20 |
| 그룹에서 제거 | 20 | 0.36초 | 0.40초 | 0.46초 | 20/20 |
| 그룹에 다시 추가 | 20 | 0.50초 | 0.55초 | 0.56초 | - |
| 그룹 해석 (위키 호출) | 200 | 2.12ms | 4.45ms | 27.63ms | - |
| 그룹 해석 (캐시 적중) | 200 | 0.21ms | 0.37ms | 1.90ms | - |

- 두 회수 경로 모두 목표(30초)보다 두 자릿수 짧고, 대부분이 아웃박스 폴링 간격(0.5초)을 기다리는 시간입니다. M3에서 잰 권한 변경의 인덱스 반영(p95 0.51초)과 같은 수준입니다.
- 본문은 위키가 요청마다 권한을 다시 판단해서, 인덱스와 캐시가 아직 반영하기 전에도 40번 모두 바로 막혔습니다. 회수 직후의 틈에 나갈 수 있는 것은 검색 결과의 스니펫뿐이고, 이 틈이 위 표의 시간입니다(ADR-07의 남는 위험).
- 다시 추가가 0.14초쯤 느린 것은, 제거가 검색에 반영된 직후 바로 추가 요청을 보내서 폴러의 다음 주기를 거의 통째로 기다리기 때문으로 봅니다.
- 그룹 해석은 위키를 불러도 p95 4.45ms로 예산(20ms) 안입니다. 로컬 환경이라 위키 호출이 빨라서, 캐시의 이득은 지연보다 검색마다 위키를 부르지 않는 데 있습니다. 배포 환경에서 위키가 다른 장비에 있으면 차이가 커지므로 M5 부하 테스트에서 캐시 적중률과 함께 다시 봅니다.

### 한계

- 노트북 한 대에서, 다른 요청이 없는 상태로 쟀습니다. 부하와 함께 재는 것은 M5입니다.
- 멤버십 이벤트 경로(아웃박스 폴러, Redis, 워커)가 멈췄을 때 캐시 TTL(60초)이 안전망이 되는 것은 설계와 단위 테스트로만 확인했고, 60초를 실제로 기다리는 측정은 하지 않았습니다.
- 처음 돌렸을 때는 측정용 문서를 끝까지 지우지 않아, 제목이 거의 같은 문서가 쌓이면서 11번째 시도 뒤 새 문서가 자기 제목 검색의 상위 5개 밖으로 밀려 시간 초과가 났습니다. 파이프라인이 아니라 측정 방법의 문제라, 시도마다 문서를 지우도록 고쳐 처음부터 다시 쟀습니다.
